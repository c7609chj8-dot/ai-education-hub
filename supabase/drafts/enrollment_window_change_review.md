# 모집 기간 저장 경로 — 실행 금지 검토안

상태: **설계 검토안이며 실행 가능한 SQL이나 마이그레이션이 아니다.** 개발·운영 DB 어디에도 적용하지 않았다. 기관의 모집 기간 정책, 변경 범위와 별도 DB 적용 승인 전에는 구현·적용하지 않는다.

2026-11-08 B-03-4 추가 결정: 관리자 입력과 화면 표시는 `Asia/Seoul`, DB의 실제 시각은 `timestamptz`, 접수 조건은 시작 포함·종료 제외로 설계한다. 두 시각이 없거나 한쪽만 있거나 같거나 역전되면 접수하지 않는다. 아래의 과거 미결 정책 메모는 당시 조사 기록이며, 최신 계획은 `docs/backend-b03-4-public-offerings.md`를 따른다. 관리자 함수·권한은 이번 공개 뷰 마이그레이션에 포함하지 않는다.

## 확인된 문제

- `academy.offerings.enrollment_opens_at`과 `enrollment_closes_at`은 기초 스키마에 이미 존재하며 둘 다 NULL이 가능하다. 기존 CHECK는 종료가 시작보다 앞서는 경우를 막지만, 두 값이 같은 경우는 허용한다.
- `day10_admin_management.sql`의 `academy_admin_save_offering`과 이를 교체하는 `day12_atomic_applications.sql` 함수는 모집 시각을 매개변수로 받거나 저장하지 않는다. 관리자 폼·서버 타입/검증/호출에도 모집 시각 입력이 없다.
- `day09_dev_offerings.sql`도 시각을 넣지 않는다. 반면 day12 신청 함수는 양쪽 시각이 존재하고 시작이 종료보다 빨라야 하며, 시작 이상·종료 미만인 경우에만 신규 접수를 허용한다. 따라서 `open` 표시만으로 접수 가능하지 않다.

## 제안할 변경 범위

아래는 최종 SQL이 아니라 리뷰어가 확인할 변경 목록이다. 기존 8개 매개변수 함수의 의미나 공개 계약을 조용히 바꾸지 않는다.

1. 기관이 모집 시작·종료의 입력 시간대, 명시적 오프셋 또는 지역 시간 사용, 시작/종료 경계, 미정 상태에서의 공개·접수 정책을 결정한다. 자동 변환이나 임의의 시작/종료 시각을 부여하지 않는다.
2. 일회용 환경에서 **새 이름의 버전된 관리자 저장 함수**를 제안한다. 예: 기존 8개 입력에 `p_enrollment_opens_at timestamptz`, `p_enrollment_closes_at timestamptz`를 더한 `academy_admin_save_offering_with_window`. 이름·서명은 최종 계약 검토 후 확정한다. 같은 이름의 다른 서명만 추가하면 구 함수와 RPC 오버로드가 남으므로 무심코 대체하지 않는다.
3. 두 시각이 모두 미정인 기수는 접수 불가로 유지하고, 한쪽만 있거나 시작이 종료 이상인 입력의 허용 여부는 정책 승인 후 명시한다. 최소한 실제 접수 허용 전에 두 값이 존재하고 시작이 종료보다 이른지 서버와 DB에서 일관되게 검증한다. 기존 DB CHECK를 강화하거나 기존 데이터를 보정할지 여부도 별도 검토한다.
4. 새 함수는 day12의 최종 구현에 있는 강좌 공개 검사, 강좌/기수 잠금 순서, 이미 접수된 수보다 낮은 정원 금지, 신청이 있는 기수의 강좌 변경 금지를 보존하면서 두 시각을 저장한다. `SECURITY INVOKER`와 빈 `search_path`를 유지하는지 검토하고, 신규 함수의 `PUBLIC`·`anon`·`authenticated` EXECUTE를 차단하고 승인된 서버 역할에만 필요한 EXECUTE/열 권한을 부여하는 방안을 같은 트랜잭션 경계에서 검증한다. 프로젝트 전체 기본 권한은 변경하지 않는다.
5. 타입·서버 검증·관리자 폼·RPC 매개변수·조회 결과·가상 seed를 함께 갱신한다. 관리자 입력을 신뢰하지 말고 서버의 인증·ID 허용목록을 유지한다. 시연 데이터에 실제 모집 시각을 임의로 넣지 않는다.
6. 구 함수가 남아 시각 없는 기수를 계속 저장할 수 있으므로, 새 서버 코드와 구 서버 인스턴스가 섞이는 배포 기간을 별도로 설계한다. 구 함수 EXECUTE 회수 또는 관리자 기능 일시 중지의 영향·순서·복구를 준비한 뒤 승인받아 시행한다. 구 함수를 지금 삭제·수정하거나 권한을 변경하지 않는다.

## 필수 검증

- 실제 개발 DB를 변경하기 전에 동일한 스키마와 가상 데이터의 격리 DB에서 NULL/한쪽 누락/같은 시각/역전/기간 전·시작 순간·종료 순간/시간대 오프셋을 확인한다. 경계는 최종 확정된 정책에 맞게 시험한다.
- 정원 1자리 경합·동일 요청 재시도·중복 이름/연락처·정원 축소 및 강좌 변경·모집 중 관리자 수정 간 경합에서 초과 접수와 교착이 없는지 확인한다.
- 관리자·일반 인증·익명·서비스 역할별 직접 RPC 및 테이블 접근, 이전 함수의 우회 가능성, 열 GRANT와 함수 EXECUTE를 확인한다. 서비스 키의 RLS 우회를 고려해 서버 경계와 로그도 검토한다.
- 승인된 개발 DB에 적용할 때는 대상 ID·이력·기존 함수/시그니처·권한·기수 데이터·백업·실행 트랜잭션과 부분 실패 복구 계획을 먼저 검토하고, SQL과 시점에 대해 별도 승인을 받는다. 현재 기능은 실제 접수에 연결되지 않았으며 이 문서는 DB 변경을 승인하지 않는다.
