# 백엔드 7일차: 관리자 접근 제어

작성일: 2026년 11월 7일

상태: **개발용 인가 구현 및 격리 검증 완료 — 실제 개발 계정 지정·실제 Supabase 요청 검증과 운영 정책 확정 대기**.

## 구현 범위

- 사용자가 선택한 개발용 사용자 ID 허용목록을 서버 전용 환경변수 `ACADEMY_ADMIN_USER_IDS`로 관리합니다. 쉼표로 구분된 Supabase Auth 사용자 UUID를 허용하며, 설정이 없거나 항목 하나라도 형식이 잘못되면 모든 관리자 접근을 거부합니다. 사용자 메타데이터나 이메일 표기를 관리자 권한의 근거로 사용하지 않습니다.
- `/admin/console`은 서버에서 `getUser()`로 인증 서버에 사용자를 확인한 후 허용된 ID인지 별도로 확인합니다. 비로그인 사용자는 로그인 화면으로, 비관리자는 권한 없음 안내로 이동합니다. 화면에는 아직 실제 운영 데이터와 관리 기능이 없습니다.
- `/api/admin/access`는 요청마다 같은 서버 측 검사를 수행하고 비로그인 401, 비관리자 403, 허용된 관리자 200을 반환합니다. 응답은 캐시하지 않습니다. 이후 추가하는 관리 API·서버 액션과 데이터 접근에도 해당 요청 안에서 인가 검사를 적용해야 합니다.
- 기존 `/admin/demo`는 실제 운영 데이터가 없는 공개 시연 화면으로 유지합니다. 로그인만으로 관리자 권한이 생기지 않으며, DB 테이블·RLS·Supabase Auth 계정이나 기존 public 객체는 변경하지 않았습니다.

## 개발 환경 설정과 제한

개발 테스트 계정은 사용자가 Supabase 대시보드에서 준비할 예정입니다. 계정 준비 후 해당 개발 프로젝트의 Auth 사용자 UUID만 개발 환경의 Git 제외 `.env.local`에 `ACADEMY_ADMIN_USER_IDS`로 설정하고 개발 서버를 재시작해 검증합니다. 비밀번호와 실제 사용자 ID를 Git이나 채팅에 기록하지 않습니다. 현재 실제 관리자 ID는 설정하지 않았으므로 기본 차단 상태입니다.

개발·Preview·운영의 Supabase 프로젝트와 허용목록은 반드시 분리해야 합니다. 환경변수 기반 목록은 변경 시 해당 서버 또는 배포의 설정 반영이 필요하며, 기존 배포에 대한 즉각적인 권한 회수를 보장하지 않습니다. 운영 전 관리자 계정 소유, 역할별 권한, 회수·복구와 감사 방식을 확정하고 별도 검증해야 합니다.

## 검증과 남은 작업

별도 가상 인증 서버와 헤드리스 브라우저에서 비로그인 화면·API 차단, 로그인된 비관리자 및 위조된 사용자 메타데이터 차단, 허용된 관리자 화면·API 접근, 무효 세션 차단, 빈 허용목록과 잘못된 허용목록의 기본 거부를 검증했습니다. 실제 Supabase 사용자·API에서의 인증과 관리자 허용·회수 검증은 아직 수행하지 않았습니다.

기존 `public.rls_auto_enable()` 보안 경고 2건은 미해결 상태로 유지합니다. 기존 3개 테이블의 정책 없음 INFO는 기본 거부 상태이며, 공개 읽기 정책과 관리자 데이터 접근은 후속 작업에서 별도 설계·검증합니다.
