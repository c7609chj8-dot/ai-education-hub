# 백엔드 12일차: 정원·중복·동시 신청 처리

작성일: 2026년 11월 7일

상태: **원자적 처리 SQL 초안과 별도 PostgreSQL 다중 세션 검증 완료. 실제 DB 적용과 실제 신청 연결은 대기.**

## 결정된 비교 기준

같은 기수에서 이름 양끝의 공백과 연락처 구분기호를 무시하고 비교합니다. 연락처는 숫자만 남겨 저장하는 후보 방식입니다. 국가번호와 국내 번호 사이의 변환, 이름 내부 공백·유니코드 표기 차이, 공동 연락처, 취소·반려 후 재신청과 자리 복귀 규칙은 확정되지 않았습니다. 신청 상태는 현재 `received`만 가정합니다.

## 준비한 초안

`supabase/drafts/day12_atomic_applications.sql`은 8~11일차 초안이 적용되고 신청 테이블이 비어 있는 경우를 전제로 합니다. 신청 요청 키와 기수별 신청자 중복 제약, 신청·개인정보의 기수 일치 제약을 추가합니다. 적용 전 기존 객체와 데이터·권한을 재확인해야 하는 **검토용 초안**입니다.

- 신청 함수는 강좌 행을 공유 잠금한 다음 기수 행을 잠그고, 현재 공개·모집 상태, 모집 기간, 정원과 중복 여부를 다시 확인합니다. 접수와 개인정보 저장을 같은 트랜잭션에서 수행해 실패하면 둘 다 롤백합니다.
- 동일 기수·동일 요청 키와 동일 내용의 재시도는 정원을 다시 차감하지 않고 기존 접수로 처리합니다. 같은 키의 다른 내용과 중복·마감·정원 부족은 공통 실패로 처리하며 신청자 정보나 신청 식별자는 반환하지 않습니다. 요청 키의 생성·전달·보관·만료와 응답 유실 후 사용자 복구 방식은 화면 연결 전 확정해야 합니다.
- 관리자 기수 수정 함수 초안을 교체해 같은 기수 잠금을 사용합니다. 접수 인원보다 정원을 줄이거나 접수된 기수의 강좌를 바꾸지 못하도록 합니다. 상태 변경 및 다른 모든 신청·취소·정원 변경 경로도 같은 잠금 규칙을 따라야 합니다.
- `SECURITY INVOKER` 함수 실행은 `service_role`에 한정하는 초안입니다. 실제 비밀 키는 프로젝트 전반에 높은 권한이 있으므로 SQL 함수의 제한이 키 자체의 권한을 제한하지 않습니다. 악용 방지·요청 제한, 서버의 활성 개인정보 안내 버전 확인, 비밀 키 관리와 DB 권한·노출 검증이 별도 필요합니다. 이름·연락처의 중복 인덱스에도 개인정보가 들어가므로 데이터·인덱스·백업 접근과 보존을 함께 관리해야 합니다.

## 격리 검증

별도 로컬 PostgreSQL 17 클러스터와 서로 다른 두 연결에서, 실제 `pg_stat_activity` 잠금 대기를 확인한 후 다음을 검사했습니다. 실제 Supabase DB는 사용하지 않았습니다.

1. 정원이 한 자리 남았을 때 두 신청 중 하나만 접수.
2. 같은 신청자의 공백·구분기호가 다른 동시 신청은 하나만 접수.
3. 동일 요청 키의 동시 재전송은 한 건만 저장하고 같은 결과 반환. 마감 이후 기존 요청 재시도도 복구.
4. 신청과 관리자 정원 축소가 어느 순서로 잠겨도 초과 접수 방지.
5. 개인정보 저장 실패 시 신청도 롤백. 비공개·마감·모집 기간 오류 차단과 기수별 중복 범위 및 외래키 제약 확인.
6. anon·authenticated의 함수 실행 차단 및 `SECURITY INVOKER` 속성 확인.

`npm run test:application-concurrency`는 새 임시 로컬 클러스터만 생성하고 테스트에만 쓰며 기존 DB 주소를 받지 않습니다. 재실행하려면 저장소 외부의 별도 폴더에 `embedded-postgres@17.11.0-beta.19`와 `pg@8.23.1`을 설치하고 `DAY12_PG_MODULE_ROOT`에 그 폴더를 지정해야 합니다. 이 의존성은 앱 빌드에 추가하지 않았습니다. PostgreSQL은 127.0.0.1에서만 실행하고 사용한 가상 데이터와 클러스터를 종료 후 정리합니다. 기존 신청·관리자·강좌·일정 테스트 및 TypeScript, ESLint, 빌드 결과는 PR에서 확인합니다.

## 실제 연결 전 남은 작업

- 8~12일차 SQL은 실제 개발 DB에 적용되지 않았습니다. 적용 전 현재 객체·마이그레이션 이력·역할 상속·Data API 접근과 롤백을 검토해야 합니다. 기존 `public.rls_auto_enable()` 보안 경고 2건은 미해결입니다.
- 실제 개인정보 수집 근거·안내 문구·보유 기간과 삭제, 중복 예외·취소, 요청 키 및 오용 방지 정책을 확정해야 합니다. 실제 개인정보는 이번 테스트에 사용하지 않았습니다.
- 현재 관리자 기수 화면은 모집 시작·종료 **시각**을 설정하지 못합니다. 초안은 두 시각이 모두 없으면 신청을 거부하므로 이를 설정하는 안전한 관리 경로가 필요합니다.
- 함수는 현재 서버나 신청 화면에 연결하지 않았으며 실제 Supabase에서 검증하지 않았습니다. 13일차 실제 화면 연결 전에 위 조건과 안내·정원·에러 처리를 검수해야 합니다. 운영 DB·main·운영 배포는 변경하지 않았습니다.
