# 백엔드 2일차 환경·배포 설계

작성일: 2026년 11월 7일

상태: **개발·운영 DB 분리 확정 — 계정·비용 및 실제 연결 대상은 미확정**. 이 문서의 환경변수와 기능 제어는 설계 제안이며 아직 구현하거나 설정하지 않았습니다.

## 1. 목적과 확인된 현재 상태

개발·검수 과정에서 현재 공개된 프런트엔드 시연에 실제 접수나 테스트 데이터가 섞이지 않도록 GitHub, Vercel, Supabase 연결 경계와 배포 절차를 정리합니다. 비회원 신청부터 시작한다는 [1일차 결정](backend-day01-requirements.md)을 전제로 합니다.

2026년 11월 7일 읽기 전용 확인 결과:

- 저장소는 `c7609chj8-dot/ai-education-hub`, `main`은 Vercel `ai-education-hub` 프로젝트의 Production 배포에 연결되어 있습니다. `main` 푸시가 실제 운영 주소 [시연 사이트](https://ai-education-hub-ten.vercel.app)의 자동 빌드·배포를 시작합니다.
- 마지막 확인한 1일차 커밋 `0da5899`의 Production 배포는 `READY`였습니다. 사이트의 신청·문의·관리자는 실제 저장이나 인증이 없는 시연입니다.
- 이 Vercel 프로젝트의 환경변수 목록에서 반환된 사용자 변수는 0개였고 숨겨진 Production 변수 수는 0개였습니다. 값의 복호화나 출력은 하지 않았습니다. 이는 조회 시점 기준이며 이후 변경될 수 있습니다.
- 저장소의 앱 코드에는 Supabase 클라이언트와 환경변수 참조가 없고, 로컬 `supabase/config.toml`과 `.vercel/project.json`도 없습니다. Git 연동은 Vercel 측에서 존재하며 로컬 Vercel 링크 유무와 별개입니다.
- 연결된 Supabase 프로젝트 목록에서 이름상 이 교육기관과 일치하는 프로젝트는 확인되지 않았습니다. 이름 검색만으로 소유·용도를 판정할 수 없으므로 기존 프로젝트를 임의로 선택하지 않았습니다. 개발·운영 계정과 비용은 미확정입니다.
- 로컬 검수 런타임은 Node.js 24.20.0 / npm 11.19.0, Vercel 프로젝트 설정은 Node.js 26.x입니다. 기존 배포는 성공했지만, 실제 백엔드 의존성 추가 시 지원 버전과 두 환경의 차이를 검증한 뒤 버전 통일 여부를 정합니다.

## 2. 환경 분리 제안

개발용과 운영용 데이터베이스의 분리는 사용자 결정으로 확정했습니다. 다음 표의 세부 연결 구조는 제안이며 실제 프로젝트 생성·연결·과금은 아직 하지 않았습니다. 운영 프로젝트는 초기에는 연결하지 않고, 담당자와 환경·예산을 확정한 뒤 준비합니다.

| 환경 | 코드와 주소 | 데이터 대상 | 허용 데이터·접근 | 실제 접수 |
| --- | --- | --- | --- | --- |
| 로컬 개발 | 개발자의 로컬 서버와 작업 브랜치 | 로컬 Supabase 또는 명시적으로 지정한 개발 전용 환경 | 가상 데이터·테스트 계정만 | 실제 접수 금지 |
| Preview | 기능 브랜치/PR별 Vercel Preview | 별도 개발·검수용 Supabase 프로젝트 또는 검증된 테스트 환경 | 가상 데이터만. 노출 범위와 접근 보호를 실제 Preview에서 확인 | 실제 접수 금지 |
| Production | `main`의 현재 Vercel 운영 주소 | 현재 연결 없음. 향후 별도 운영 전용 프로젝트 제안 | 실제 운영 시 승인된 계정과 최소 권한만 | 준비·검수 완료 전 비활성 |

확정된 개발·운영 DB 분리를 위해 별도 Supabase 프로젝트 사용을 권장합니다. 프로젝트의 구체적인 구성과 소유 계정은 아직 정하지 않았습니다. 테스트용 한 프로젝트를 여러 Preview가 공유하면 데이터와 마이그레이션이 서로 영향을 줄 수 있습니다. 동시 검수 시에는 프로젝트별 테스트 데이터 구분과 적용 순서를 관리하고, 필요하면 비용·한도를 확인해 격리된 환경을 마련합니다. 테스트 환경 초기화도 대상 프로젝트와 데이터 보존 여부를 먼저 확인하며 운영·타 프로젝트에 실행하지 않습니다.

## 3. 코드·배포 흐름

1. 후속 백엔드 코드는 `codex/` 접두사 기능 브랜치에서 작성하고 GitHub에 푸시합니다. 브랜치 푸시와 PR이 Preview를 만드는지는 실제 저장소 연동과 보호 설정에서 검증합니다. 현재 조회된 Preview 배포 이력은 없습니다.
2. 마이그레이션과 정책은 버전 관리되는 코드로 검토하고 로컬/개발 환경에서 가상 데이터로 먼저 적용·검증합니다. 변경 대상 프로젝트를 명시적으로 확인합니다.
3. Preview가 개발 전용 데이터만 사용하도록 확인한 뒤 공개 강좌·비회원 신청·문의·관리자 인증과 실패·권한 거부를 검수합니다. 무신뢰 포크의 실행 코드에 비밀값을 제공하지 않습니다.
4. Production 반영 시에는 이전 호환성을 고려한 확장→전환→정리 순서로 DB와 코드를 설계합니다. 백업·복구 방안과 기능 비활성 상태를 먼저 확인하고, 검수한 코드와 스키마를 반영합니다.
5. `main`에 합치면 현재 연결 설정상 Production 자동 배포가 시작됩니다. 문서 변경도 배포를 시작할 수 있으므로 배포 상태와 대상 커밋을 확인합니다. 운영 기능은 서버 측 검증 완료와 전환 준비 전까지 꺼진 상태를 유지합니다.

현재 2일차는 설계·문서 작업입니다. 기능 브랜치 생성, PR, Vercel 변수 변경, Supabase 프로젝트 생성·연결 및 DB 마이그레이션은 이번 작업에서 실행하지 않았습니다.

## 4. 실제 접수 전환 제어 — 구현 예정

- 서버에서 확인하는 별도 접수·문의 기능 제어를 제안합니다. 값이 없거나 해석할 수 없을 때는 **비활성**으로 취급하며, 클라이언트의 버튼 숨김만으로 보호하지 않습니다.
- 비활성 시 실제 쓰기 요청은 서버에서 거부하고, 화면에는 시연 또는 준비 중 상태를 표시합니다. 가짜 성공 응답으로 실제 접수된 것처럼 표시하지 않습니다.
- 개발·Preview에서만 테스트 데이터로 기능을 검증합니다. Production은 개인정보 정책·관리자 인증·정원·동시성·권한·복구 검수가 끝난 뒤 별도로 전환합니다.
- 기능 제어는 보안 권한 검사의 대체가 아닙니다. 실제 기능이 활성화된 뒤에도 각 요청에서 서버 권한 확인, 입력 검사, 접근 정책 및 정원 트랜잭션을 적용합니다.
- 관리자 실제 경로는 `/admin/demo`와 분리하고 로그인과 역할을 서버에서 검증합니다. 시연 경로에는 실제 신청 데이터를 연결하지 않습니다.

## 5. 환경변수·비밀값 설계 초안

아래는 **향후 구현 후보**입니다. 변수명·보관 방법은 실제 라이브러리와 구조를 정할 때 확정합니다. 현재 어떤 값도 추가하지 않았으며, 환경별로 검증 전까지 비어 있습니다.

| 구분 | 예시 또는 용도 | 공개 범위 | 대상·원칙 |
| --- | --- | --- | --- |
| 서비스 주소 | Supabase 프로젝트 URL | 공개 가능 | 로컬/Preview는 개발 대상, Production은 운영 대상만 |
| 공개용 키 | Supabase publishable key | 브라우저에 노출될 수 있음 | 비밀키가 아니며 단독 권한 보호 수단이 아님. GRANT·RLS 필수 |
| 서버 비밀값 | 필요한 경우에만 사용하는 서버 전용 비밀 | 서버 전용 | 최소 권한과 사용처를 검토. 브라우저·로그·Git에 넣지 않음 |
| 실제 접수 제어 | 서버에서 확인하는 접수/문의 활성화 설정 | 서버 전용 제안 | 환경마다 별도로 관리하며 기본값은 비활성 |
| 환경 식별 | 테스트·운영 대상 확인용 설정 | 민감도에 맞게 분리 | 실제 대상과 예상 대상이 다르면 쓰기를 거부 |

`NEXT_PUBLIC_` 접두사가 붙은 값은 브라우저 번들에 노출될 수 있으므로 비밀키·DB 암호를 넣지 않습니다. Supabase의 비밀키나 서비스 역할 키는 RLS를 우회할 수 있어 공개 클라이언트에 사용하지 않습니다. 실제 필요가 확인되기 전에는 고권한 키를 도입하지 않으며, 서버에서 쓰더라도 권한 검사를 별도로 수행합니다. 환경별 값은 Vercel 환경변수와 로컬 Git 제외 파일에서 관리하고 채팅·README·로그에 적지 않습니다. 현재 `.gitignore`는 `.env*` 전체를 제외하므로, 값 없는 변수 목록은 문서에 두거나 추후 예제 파일의 추적 방식을 명시적으로 정합니다.

## 6. 데이터와 마이그레이션

- 개발과 운영의 대상 프로젝트 식별자는 **값을 문서나 로그에 노출하지 않는 방식으로** 각각 관리하고, 작업 전 연결 대상과 환경을 확인합니다.
- 신규 마이그레이션은 로컬에서 작성·검토하고 가상 데이터로 반복 적용을 검증합니다. Preview 대상에 적용하기 전 기존 상태·백업·동시 사용 여부를 확인합니다.
- Supabase CLI v3는 DB 명령이 기본적으로 로컬을 대상으로 동작하며 원격 처리 방식이 달라졌습니다. 설치 버전의 `--help`와 [공식 변경 안내](https://supabase.com/changelog/supabase-cli-v3)를 확인하고 대상을 추측하지 않습니다.
- 노출되는 데이터는 객체 GRANT와 RLS를 함께 설정하고, 공개 사용자·운영자·권한 없는 사용자별 접근을 실제 테스트합니다. 관리자만 볼 신청·문의는 공개 목록으로 노출하지 않습니다.
- 운영 스키마 변경 전 백업·복구 가능 여부와 코드 호환성을 검증합니다. 프런트엔드 배포 롤백은 DB 스키마·데이터를 되돌리지 않으므로 별도의 복구 절차가 필요합니다.

## 7. 전환·검수·복구 체크리스트

실제 설정·전환 전에 아래 결과를 기록합니다.

1. 대상 Git 커밋·Vercel 환경·Supabase 프로젝트가 계획한 조합인지 확인하고, Preview에서 운영 DB 쓰기가 불가능한지 검증합니다.
2. 공개 키로 비공개 신청·문의·파일에 접근할 수 없고, 비관리자·만료 세션·권한 회수 계정이 관리자 요청에 실패하는지 검사합니다.
3. 실제 접수 제어가 비활성일 때 직접 API 요청도 저장하지 못하며 가짜 접수 성공을 표시하지 않는지 확인합니다.
4. 활성 검수는 개발 환경의 가상 데이터로만 수행하고, 정원 1자리 동시 요청·중복 요청·실패 재시도를 확인합니다.
5. Preview 접근 보호, 프런트·서버 로그의 개인정보·비밀값, 환경변수 노출을 점검합니다. Production 전환 전 개인정보 안내·보존 기간·운영 담당자를 확정합니다.
6. 운영 DB의 백업과 별도 테스트 환경 복원, 적용 실패·기능 비활성화·프런트엔드 롤백·DB 복구 순서를 리허설합니다. 복구 시점 및 데이터 손실 가능 범위를 문서화합니다.
7. 의존성 감사와 Node 버전 호환성, 실제 배포 상태·도메인·핵심 페이지를 재확인합니다. 19일차 기준 개발 의존성의 중간 등급 경고 8건은 별도 검토 대상입니다.
