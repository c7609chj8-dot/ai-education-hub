# 백엔드 25일차: 운영 전환 준비와 인수인계

작성·점검일: 2026년 11월 8일 (한국 시간)

**현재 판정: 운영 전환 보류.** 25일차 문서 준비는 실제 서비스 완성, 운영자 인수 또는 배포 승인을 의미하지 않습니다. 공개 신청·문의는 입력 과정만 시연하며 실제로 접수하지 않습니다. 실제 운영 기능 연결과 검증, 기관의 운영 정책 결정 및 별도 전환 승인이 필요합니다.

## 25일차 이후 보안 상태 확인

2026년 11월 8일 후속 보안 작업에서 개발 프로젝트 `uenvjqgylrevujdjpfed`에 `20261108064422_restrict_rls_auto_enable_execute`가 적용됐습니다. 현재 개발 DB 이력은 기존 `20261107100302_academy_course_foundation`을 포함해 두 건입니다. 기존 `public.rls_auto_enable()` 관련 Security Advisor WARN 2건은 후속 검사에서 조회되지 않았고, 정책 없는 기초 테이블의 INFO 3건은 남아 있었습니다.

함수 정의와 `ensure_rls` 트리거는 유지됐고 일회용 테이블 생성 후 자동 RLS 활성화와 롤백을 개발 DB에서 확인했습니다. `PUBLIC` 실행 권한 회수로 `service_role`과 `authenticator`의 상속 실행 권한도 없어졌습니다. 실제 서비스 역할 API와 외부 관리 도구의 호환성은 미검증입니다. 상세 변경과 검증 범위는 [보안 수정 기록](security-rls-auto-enable.md)을 따릅니다.

아래 표와 차단 항목은 **25일차 점검 당시의 이력**입니다. 당시의 마이그레이션 1건과 WARN 2건 설명을 현재 상태로 해석하지 않습니다. 보안 PR #23의 Git 통합은 이 문서를 포함한 별도 통합 브랜치에서 검토 중이며 `main` 병합이나 운영 배포는 승인되지 않았습니다.

## 향후 전환 순서 — 실행 전 별도 승인 필요

1. 위 차단 항목과 담당자·변경 창·승인자를 확정합니다. 개발·운영 프로젝트 ID, Vercel 팀·프로젝트·환경, 배포 커밋, 도메인, 백업 및 변경 전 상태를 담당자가 각각 대조합니다. 비밀번호나 키 값은 문서·채팅·로그에 기록하지 않습니다.
2. 변경 대상의 현재 마이그레이션 이력과 객체·권한·데이터를 읽기 전용으로 비교하고, 기존 초안을 실제 대상에 맞게 별도로 검토합니다. 승인된 격리 환경에서 가상 데이터로 순서·중복·권한·복구를 시험합니다. 개발 DB 적용과 운영 DB 적용은 각각 범위와 시점을 확인한 뒤 별도 승인합니다.
3. 실제 운영 데이터 대신 가상 데이터로 실제 개발 API와 Auth·Storage를 검사하고 Preview의 연결·보호·결과를 확인합니다. 신청·문의의 실제 저장 연결, 차단 수단, 예외 복구 및 관리자 계정이 준비되기 전에는 시연 표시를 유지합니다.
4. 승인된 운영 데이터·정책·계정과 복구 지점을 준비한 뒤 운영자가 인수 시험을 수행하고 결함을 해결합니다. PR 연쇄와 각 변경사항을 검토합니다. 현재 PR #1의 대상은 `main`이며 병합 시 Production 자동 배포 가능성이 있으므로 병합 자체를 운영 변경으로 취급합니다.
5. 별도 전환 승인 후에만 검증된 배포·환경·DB 조합을 적용합니다. 승인된 실제 연결의 공개 조회·접근 차단·신청/문의·관리자·로그를 검증한 결과와 대상 커밋을 기록합니다. 실패 시 추가 변경을 중단하고 아래 대응 계획을 따릅니다.

## 장애·복구 계획 — 실제 복원 미시험

1. 담당자는 영향·시작 시각·대상 환경과 최근 배포/DB 변경을 확인하고 신규 쓰기의 안전한 중단 방법을 결정합니다. 현재 실제 접수 경로는 없고 전역 중지 스위치는 검증돼 있지 않으므로, 이를 이미 사용할 수 있다고 가정하지 않습니다.
2. 코드 배포 복구와 DB·Storage 복구는 별개입니다. 이전 배포로 되돌릴 경우에도 현재 스키마·데이터·기능 설정과 호환되는지 확인하고 실제 롤백 전에 승인합니다. [Vercel 롤백 문서](https://vercel.com/docs/deployments/rolling-back-a-deployment)
3. 복원점 이후 신청·문의 데이터의 유실·중복 범위와 원본 보존 방법을 확인합니다. 승인된 격리 대상에서 실제 DB 복원·권한·정원·이력과 Storage 객체 및 정책을 각각 대조한 뒤 운영 복구를 결정합니다. DB 백업만으로 Storage 파일이 복구되는 것으로 가정하지 않습니다. [Supabase 백업 문서](https://supabase.com/docs/guides/platform/backups)
4. 실서비스 복구와 재개는 기관 담당자가 검증·승인하고, 고객 안내·이후 신청 대조·원인 분석을 기록합니다. 개인정보와 비밀값은 장애 기록에서 제외합니다. 세부 준비·로컬 복원 한계는 [22일차 문서](backend-day22-backup-recovery.md)를 따릅니다.

## 설정 인계 — 이름과 용도만

- `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`: 클라이언트에 공개 가능한 연결 정보입니다. 현재 코드는 승인된 **개발 프로젝트 원본만** 허용합니다. `NEXT_PUBLIC_`에는 비밀키를 넣지 않습니다.
- `SUPABASE_SECRET_KEY`: 서버 전용 고권한 비밀값입니다. 서버에서만 사용하고 범위·보관·교체·노출 여부를 별도 검토합니다.
- `ACADEMY_ADMIN_USER_IDS`: 관리자 사용자 ID 허용목록입니다. 실제 계정 등록·회수와 재검증은 아직 미완료입니다.
- `ACADEMY_ADMIN_MANAGEMENT_ENABLED`, `ACADEMY_ADMIN_APPLICATIONS_ENABLED`, `ACADEMY_ADMIN_INQUIRIES_ENABLED`, `ACADEMY_ADMIN_CONTENT_ENABLED`, `ACADEMY_ADMIN_ASSETS_ENABLED`, `ACADEMY_ADMIN_BRAND_ENABLED`, `ACADEMY_ADMIN_AUDIT_ENABLED`: 각 관리자 기능의 서버 측 제한입니다. 이 설정만으로 인가·RLS·모든 쓰기 차단이 보장되는 것은 아닙니다.
- `ACADEMY_COURSE_SOURCE`, `ACADEMY_CONTENT_SOURCE`, `ACADEMY_ASSET_SOURCE`, `ACADEMY_BRAND_SOURCE`: 공개 데이터 원본 선택입니다. 기본은 `mock`이며 실제 원격 연결에는 별도 조건이 있습니다. 일정은 강좌 원본 설정을 따릅니다.
- `ACADEMY_COURSE_DEMO_DATA`, `ACADEMY_SCHEDULE_DEMO_DATA`, `ACADEMY_PUBLIC_ASSETS_ENABLED`: 시연 표시 또는 공개 자료 접근 관련 설정입니다. 값을 바꿔 시연 표시를 감추는 것만으로 데이터가 실제 운영 정보로 승인되는 것은 아닙니다.

환경변수는 환경별로 따로 검토하고, 빌드에 영향을 주는 값은 대상 빌드·런타임 조합에서 다시 확인합니다. [Vercel 환경변수 문서](https://vercel.com/docs/environment-variables)
