## 격리 환경 결과

`npm run test:b03-6-offering`은 실제 SQL과 서버 입력 검증 코드를 사용하되 PGlite 메모리 DB와 가상 관리자·사용자를 사용한다. 강좌 5개·주차 60개를 가상 데이터로 만든 뒤 비공개 draft 1개의 등록, 목록 조회, 위치 수정, 정원 10명, 한국 시각 UTC 변환과 왕복, 잘못된 기간·음수 정원·공개 draft 거부, 같은 입력의 중복 거부, 일반 사용자와 익명 사용자 쓰기 거부 및 공개 뷰 비노출을 확인했다. 가상 기수만 삭제한 뒤 강좌 5개·주차 60개·기수 0개·가상 관리자 1개를 확인했다.

`npm run test:admin-offerings-v2-postgres`는 별도 로컬 PostgreSQL 17.11에서 가상 역할·사용자를 사용한다. 제한된 비슈퍼유저 환경에서 v2 등록·수정, 직접 쓰기 및 비인가 실행 거부, 오류 롤백과 자동 RLS 이벤트 트리거 유지, 동일한 두 비공개 draft 동시 요청의 잠금 대기와 1건만 생성됨을 확인했다. 가상 기수는 정확한 UUID로 정리했고 임시 DB를 중지·제거했다. 이 환경은 실제 Supabase 호스팅의 모든 동작을 재현하지는 않는다.

**중복 기준의 한계:** 현재 RPC는 강좌·날짜뿐 아니라 장소 등 입력값이 모두 같은 경우를 중복으로 취급한다. 동일 강좌와 같은 교육기간이라도 장소가 다르면 새 기수로 저장될 수 있음을 격리 트랜잭션에서 확인하고 롤백했다. 따라서 '동일 강좌·교육기간이면 무조건 중복'은 보장하지 않는다. 업무 기준을 정한 뒤 별도 설계·승인해야 하며, 위 동시성 결과도 동일 입력에 한정된다.

정원 0은 draft에 허용될 수 있고 모집 중인 기수는 별도 조건이 적용된다. 여기서 음수 정원 거부를 확인했으며, 신청 접수·정원 차감의 실제 DB 동작을 검증한 것은 아니다.

### 별도 승인 1 — 등록

1. 현재 개발 프로젝트 ID, 대상 강좌, 위 UUID 미사용, 강좌 5·주차 60·기수 0, 관리자 1·Auth 사용자 2, 현재 로그인 사용자와 DB 관리자 목록을 읽기 전용으로 다시 검사한다.
2. 최신 DB 백업과 무결성 및 복구 범위를 확보한다. 특히 기존 백업은 현재 관리자·일반 사용자 생성 이후의 완전한 복구를 보장하지 않는다. 호스팅 Auth의 복원 한계가 해소되지 않으면 이를 명확히 보고하고 승인 범위와 복구 수단을 다시 확인한다.
3. **등록 승인을 받은 뒤에만** 실제 관리자 세션의 사용자 JWT를 사용해 기존 서버/API 및 v2 RPC로 표의 비공개 기수 1건을 만든다. 유효하지 않은 요청, 일반 사용자·미로그인 요청은 기존 승인 범위와 충돌하지 않도록 실제 데이터 변경을 일으키지 않는 방식으로 별도 검토한다.
4. 정확한 UUID의 값, 한국 시간 변환, 건수, 익명 공개 일정 API 비노출, 기존 강좌·주차 및 사용자 상태를 확인한다. 요청 실패 또는 타임아웃에는 재시도하지 않고 UUID·DB·마이그레이션 상태를 읽기 전용 조회한다.

### 별도 승인 2 — 수정

등록 결과와 현재 행의 모든 값, 의존 데이터를 확인한 후에만 수정 승인을 요청한다. 승인되면 같은 UUID의 장소만 표의 수정 값으로 바꾸고, 승인한 단 한 건 외에는 변경하지 않는다. 수정 후 시간·정원·비공개 상태 및 공개 API 비노출을 다시 확인한다. 수정 전후 데이터는 복구할 수 있도록 기록하되 사용자 정보·토큰은 남기지 않는다.

### 별도 승인 3 — 정리

시험 종료 후 정확한 UUID와 강좌 ID 및 기대 필드가 맞는지, 신청 등 참조 데이터가 없는지 외래키와 실제 행을 조회한다. 참조가 있거나 내용이 예상과 다르면 삭제를 중단한다. 별도 정리 승인을 받은 후 정확한 UUID 한 건만 트랜잭션으로 삭제하고 영향 행 수가 1인지 확인한다. 기수 전체 삭제, CASCADE, 강좌·사용자 삭제는 허용되지 않는다. 정리 후 5개·60개·0개와 계정 및 공개 조회를 다시 확인한다.

### 중단 및 복구

오류·연결 끊김·타임아웃·예상 밖 데이터가 있으면 쓰기를 중지하고 같은 요청을 재실행하지 않는다. 프로젝트와 기수 UUID로 현재 상태 및 변경 범위를 읽기 전용으로 확인한 뒤 사용자에게 결과와 최소 복구안을 보고한다. 대량 초기화나 기존 백업의 통째 복원은 수행하지 않는다. 현재 운영 데이터와 Auth의 완전 복원은 보장되지 않는다.

## 미검증 및 범위

- 실제 개발 DB 등록은 아래와 같이 한 번 시도했으나 생성되지 않았다. 수정·삭제, 실제 시험 기수의 공개 차단, 실제 JWT를 이용한 저장 성공과 동시 요청은 미검증이다.
- 관리자 권한 회수와 실제 모집·신청·정원 차감은 이 단계에서 수행하지 않는다.
- 실제 DB 스키마, RLS, GRANT, 마이그레이션을 변경하지 않으며 main 병합과 운영 배포도 하지 않는다.

## 2026-11-09 개발 DB 등록 시도 중단 기록

- 최신 수동 백업의 기준 값은 강좌 5, 주차 60, 기수 0, Auth 사용자 2, 관리자 1, 마이그레이션 5다. 백업 파일 4개의 SHA-256은 모두 일치하고 아카이브 목록에 강좌·주차·Auth 사용자·관리자 목록·이력 데이터가 있다. **해당 최신 백업의 복원 시험과 Supabase Auth·역할·이벤트 트리거 전체 복원은 미검증**이다. Storage 객체와 버킷은 기준 조회에서 0건이었다.
- 등록 직전 개발 DB는 같은 건수였고, 승인된 강좌와 관리자 계정이 존재하며 시험 UUID는 사용 중이 아니었다. 실제 로그인 세션의 관리자 화면 접근을 확인했다.
- 정해진 UUID를 기존 서버 액션에 전달하기 위한 일회성 로컬 화면에서 승인된 값으로 등록을 한 번 요청했으나, 화면은 `저장 결과를 확인하지 못했습니다`를 반환했다. 작성자는 재시도하지 않았다. 즉시 읽기 전용 조회한 결과 기수는 여전히 0건이고 해당 UUID도 0건이었다. 강좌 5·주차 60·Auth 사용자 2·관리자 1은 유지됐으며, 익명 공개 API도 강좌 5·주차 60·기수 0을 반환했다.
- 원인: 별도 로컬 서버를 준비하면서 `ACADEMY_ADMIN_MANAGEMENT_ENABLED=true`를 설정하지 않았다. 서버 액션의 `authorizedOfferingClient()`는 이 값이 없으면 저장 RPC 호출 전에 중단하고 `unknown`을 반환한다. 이는 테스트 서버 준비 시 사전 점검 누락이다. 관리자 JWT 검증 성공과 저장 기능 활성화 여부는 서로 다르다.
- 일회성 로컬 시험 화면은 삭제하고 해당 테스트 서버만 종료했다. 실제 기수 생성·수정·삭제는 없었고 DB 스키마와 권한도 변경하지 않았다.
- 후속 시도는 사용자에게 보고하고 다시 지시를 받은 뒤 진행한다. 그때 개발 전용 테스트 서버의 플래그를 프로세스에만 설정하고, 프로젝트·관리자 세션·백업·대상 UUID와 기존 건수를 다시 확인해야 한다. 저장 오류 또는 불확실한 응답에는 재시도하지 않고 실제 DB를 읽기 전용으로 조사한다.
