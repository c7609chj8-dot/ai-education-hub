## 2026-11-09 개발 DB 등록 시도 중단 기록

- 최신 수동 백업의 기준 값은 강좌 5, 주차 60, 기수 0, Auth 사용자 2, 관리자 1, 마이그레이션 5다. 백업 파일 4개의 SHA-256은 모두 일치하고 아카이브 목록에 강좌·주차·Auth 사용자·관리자 목록·이력 데이터가 있다. **해당 최신 백업의 복원 시험과 Supabase Auth·역할·이벤트 트리거 전체 복원은 미검증**이다. Storage 객체와 버킷은 기준 조회에서 0건이었다.
- 등록 직전 개발 DB는 같은 건수였고, 승인된 강좌와 관리자 계정이 존재하며 시험 UUID는 사용 중이 아니었다. 실제 로그인 세션의 관리자 화면 접근을 확인했다.
- 정해진 UUID를 기존 서버 액션에 전달하기 위한 일회성 로컬 화면에서 승인된 값으로 등록을 한 번 요청했으나, 화면은 `저장 결과를 확인하지 못했습니다`를 반환했다. 작성자는 재시도하지 않았다. 즉시 읽기 전용 조회한 결과 기수는 여전히 0건이고 해당 UUID도 0건이었다. 강좌 5·주차 60·Auth 사용자 2·관리자 1은 유지됐으며, 익명 공개 API도 강좌 5·주차 60·기수 0을 반환했다.
- 원인: 별도 로컬 서버를 준비하면서 `ACADEMY_ADMIN_MANAGEMENT_ENABLED=true`를 설정하지 않았다. 서버 액션의 `authorizedOfferingClient()`는 이 값이 없으면 저장 RPC 호출 전에 중단하고 `unknown`을 반환한다. 이는 테스트 서버 준비 시 사전 점검 누락이다. 관리자 JWT 검증 성공과 저장 기능 활성화 여부는 서로 다르다.
- 일회성 로컬 시험 화면은 삭제하고 해당 테스트 서버만 종료했다. 실제 기수 생성·수정·삭제는 없었고 DB 스키마와 권한도 변경하지 않았다.
- 후속 시도는 사용자에게 보고하고 다시 지시를 받은 뒤 진행한다. 그때 개발 전용 테스트 서버의 플래그를 프로세스에만 설정하고, 프로젝트·관리자 세션·백업·대상 UUID와 기존 건수를 다시 확인해야 한다. 저장 오류 또는 불확실한 응답에는 재시도하지 않고 실제 DB를 읽기 전용으로 조사한다.

## 저장 중단 경로 재현 및 읽기 전용 연결 점검

- 기존 서버 로그에는 일회성 테스트 화면의 `submitOffering` POST와 불확실한 결과가 기록됐지만 RPC 오류 본문은 기록되지 않았다. 당시 화면은 일반 기수 폼이 아니라, 승인된 UUID와 값을 기존 서버 액션에 전달한 임시 화면이었다.
- 당시 로컬 서버는 개발용 URL과 공개 키만 프로세스에 설정했고, 작업 폴더에 환경 파일도 없었다. 관리자 화면과 서버 액션은 세션과 DB 관리자 확인을 통과했으나, `authorizedOfferingClient()`는 `ACADEMY_ADMIN_MANAGEMENT_ENABLED`가 정확히 `true`가 아니어서 클라이언트를 생성하지 않고 중단한다. 이 경로는 `unknown`을 반환하므로 화면의 문구만으로 실제 네트워크 오류와 구분되지는 않는다.
- 회귀 검사에서 설정 누락 및 `false`는 관리자여도 클라이언트와 RPC 호출이 0건이고, `true`에서는 가상 사용자 세션으로 v2 RPC가 호출되는 것을 확인했다. 우회하거나 권한을 넓히지 않는다.
- 입력 검증과 한국 시간 변환은 격리 PGlite에서 원래 승인된 날짜·시간과 비공개·정원 10의 값을 사용해 확인했다. 09:00 KST는 00:00 UTC, 18:00 KST는 09:00 UTC로 변환된다. 이 검사는 이전 실제 요청이 RPC에 도달해 저장됐다는 증거는 아니다.
- 설정을 로컬 프로세스에만 켠 다음, 기존 실제 관리자 세션에서 기수 관리 목록을 읽기 전용으로 열었다. 서버가 강좌 5개와 기수 없음 화면을 반환했으며 비밀 키는 사용하지 않았다. 시험 서버는 확인 후 종료했다.
- 관리자 인증·서비스·입력·폼·액션 회귀, PGlite와 로컬 PostgreSQL 17.11의 RPC·동시성 검사, ESLint, TypeScript가 통과했다. 최초 TypeScript 확인은 이미 삭제한 일회성 화면의 오래된 Next 생성 타입 때문에 실패했으며 해당 생성 파일만 제거한 후 통과했다. 기본 `npm run build`는 환경 파일이 없는 별도 물리 복사본에서 Turbopack으로 통과했다.
- 현재 실제 개발 DB에서 강좌 5개, 주차 60개, 기수 0건, Auth 사용자 2명, 관리자 1명과 대상 UUID 0건을 재확인했다. 저장 요청은 다시 보내지 않았다.
- 재등록 가능성은 설정·인증·격리 결과를 근거로 판단하되, 실제 저장 RPC의 성공과 비공개 기수의 실 API 비노출은 저장 전에는 확인할 수 없다. 대상 서버 설정·세션·DB 현황·백업 해시를 실행 직전에 재확인하고 **별도 승인을 받은 뒤에만** 기존에 제안한 UUID로 한 번 시도한다. 수정·삭제·공개는 각각 별도 승인 대상이다.
