# B-03-5 실제 세션·RPC 보안검증

검증일: 2026-11-09. 대상은 개발 프로젝트 `ai-education-hub-dev`다. 비밀번호, JWT, 사용자 이메일과 API 키를 기록하지 않는다. 실제 교육기수의 생성·수정·삭제는 수행하지 않았다.

## 실제 사용자별 결과

| 항목 | 관리자 JWT | 일반 사용자 JWT | 미로그인 |
| --- | --- | --- | --- |
| `academy_is_admin_v2` 직접 호출 | `true` | `false` | `42501` |
| `academy_admin_save_offering_v2` 잘못된 입력 | 모두 `22023 / Invalid offering` | 권한 검사에서 `42501` | `42501` |
| 관리자 화면·접근 API | 화면 허용 / API 200 | 거부 화면 / API 403 | 로그인 페이지 / API 401 |

실제 세션은 사용자가 관리자와 일반 사용자로 각각 로그인해 만들었다. 로컬 개발 서버의 일시적 검증 경로는 사용자 세션으로 Supabase Auth `getUser()`와 RPC를 직접 호출하고 결과 코드와 참·거짓만 반환했다. JWT와 계정 정보를 출력·저장하지 않았다. 이 경로는 시험 종료 후 제거했고 HTTP 404를 확인했다. 보안 검증 시점의 실제 저장 함수 본문 해시가 검토한 후보와 일치하는 것을 확인했다.

관리자의 잘못된 입력은 ID 누락, 음수 정원, 공개된 작성 중 상태, 모집기간 누락·역전, 모집 중 정원 0건이다. 각각 원인에 맞는 필드만 바꿨고 데이터가 없는 강좌 ID를 추가 안전장치로 사용했다. 모든 호출은 저장 구문 전 `Invalid offering`으로 거부됐다. 일반 사용자와 미로그인 사용자는 동일 RPC에서 입력 검사보다 먼저 권한 오류를 받았다. 성공하는 저장·수정은 시험하지 않았다.

일반 사용자 JWT로 `academy.offerings`에 직접 INSERT·UPDATE·DELETE를 요청했을 때 세 요청 모두 HTTP 406 / `PGRST106`으로 거부됐다. 이는 **Data API의 비노출 스키마 차단**이며 PostgreSQL 권한 거부와 구분한다. 별도의 실제 DB 카탈로그 조회에서는 일반 인증 역할의 해당 테이블 INSERT·UPDATE·DELETE 및 모든 열의 INSERT·UPDATE 권한이 없었다. 시험용 ID는 존재하지 않았고, 삽입 시도에는 필수 NOT NULL 값도 누락했다.

관리자는 `127.0.0.1`, 일반 사용자는 `localhost`의 분리된 브라우저 쿠키로 시험했다. 일반 사용자 확인 → 관리자 확인 → 일반 사용자 재확인 순서에서 각각 거부·허용·거부가 유지됐다. 이는 해당 두 로컬 호스트 세션의 결과이며 다른 브라우저나 도메인까지 보장하지 않는다.

시험 전후 실제 개발 DB의 강좌 5개·주차 60개·기수 0개, 관리자 1명, Auth 사용자 2명이 유지됐다. 익명 권한 차단, 일반 사용자 권한 차단, 관리자 입력 오류와 기존 데이터 유지 결과를 혼동하지 않는다.

## 코드·빌드 회귀 검사

- TypeScript `tsc --noEmit --incremental false`와 ESLint가 통과했다.
- 관리자 인증 게이트, 기수 RPC v2 격리 테스트, 기수 서비스, 관리자 입력 검증, 기수 폼 테스트가 통과했다. 격리 테스트의 가상 사용자와 이번 실제 세션 테스트는 별도다.
- 기존 로컬 개발 서버를 보호하기 위해 동일 Git 커밋의 독립 스냅샷에서 기본 `npm run build`를 실행했다. 첫 실행은 임시 `node_modules` 연결이 Turbopack의 작업 폴더 밖을 가리켜 실패했다. 의존성을 임시 폴더 안에 복사한 뒤 재실행한 기본 Turbopack 빌드는 통과했다. 사용자 프로젝트 설정이나 배포는 변경하지 않았다.

## 남은 위험과 권한 회수 검증 계획

- 실제 관리자 저장·수정, 직접 권한 회수 후 기존 JWT, 동시 요청과 정원 적용은 이번 실제 개발 DB에서 시험하지 않았다. 격리 가상 데이터 테스트 결과를 실제 JWT 검증으로 간주하지 않는다.
- 유일한 관리자를 회수하지 않는다. 먼저 로컬 격리 DB에서 가상 사용자와 동일 권한 모델로 회수·진행 중 요청을 재현한다. 실제 JWT 재검증이 필요하면 기존 관리자를 유지하면서 두 번째 임시 관리자의 등록과 회수를 각각 명시적으로 승인받고, 같은 JWT로 회수 전 허용·회수 커밋 뒤 시작한 요청 거부를 확인한다. 진행 중 문장, 남아 있는 일반 로그인 세션 및 JWT 자체의 만료·폐기는 별도 한계다.
- Security Advisor는 유출 비밀번호 보호 미사용 WARN 1건과 클라이언트 정책이 없는 관리자 목록의 RLS INFO 1건을 보고한다. 이 INFO를 없애기 위해 무분별한 정책을 추가하지 않는다.

## 실제 일정 등록·수정 시험 제안 — 승인 전

1. 단일 개발 프로젝트·백업·기수 0건과 실제 관리자 세션을 다시 확인하고, 공개 화면에 표시되지 않도록 고유한 가상 기수 하나를 `draft`, `is_public=false`로만 준비한다.
2. 적용 전 선택할 강좌와 실제 날짜·모집 시각·정원, 생성·수정 대상 UUID, 테스트 종료 후 삭제할 정확한 행과 검증 방법을 제시한다. 생성·수정·정리의 범위는 사용자가 명시적으로 승인하기 전 확정하거나 실행하지 않는다.
3. 승인 후 관리자 JWT로 등록·단일 값 수정·중복 처리와 공개 비노출을 검증하고, 각 단계의 데이터 상태를 기록한다. 일반 사용자와 미로그인 거부는 검증하되 실제 수강생 개인정보를 사용하지 않는다.
4. 정리는 승인된 정확한 시험 행만 대상으로 하고, 정리 실패·타임아웃 시 재시도하지 않는다. 남은 행과 의존성을 읽기 전용으로 확인하고 별도 복구안을 제시한다. 종료 후 기수 0건 및 강좌 5개·주차 60개, 권한·RLS와 기존 공개 조회를 확인한다.
