# 백엔드 22일차: 백업·복구 및 장애 대응 연습

작성일: 2026년 11월 8일 (한국 시간)

상태: **가상 로컬 PostgreSQL의 오프라인 물리 백업·별도 복원 연습과 대응 절차를 준비했습니다. 실제 Supabase 백업 및 복원은 검증하지 않았습니다.**

## 복구 목표와 범위

기관의 결정에 따라 목표 복구 시간(RTO), 허용 데이터 손실 범위(RPO), 보존 기간, 담당자·승인자는 운영 시작 전에 별도로 확정합니다. 아래 로컬 측정치는 실제 서비스의 복구 시간이나 보장 수준이 아닙니다.

공식 문서에 따르면 PostgreSQL 파일 시스템 백업은 DB 서버를 완전히 종료한 뒤 **전체 클러스터**를 대상으로 해야 하며, 단일 테이블 디렉터리만 복사해 복구할 수 없습니다. [PostgreSQL 17 파일 시스템 백업](https://www.postgresql.org/docs/17/backup-file.html)

Supabase 데이터베이스 백업에는 Storage API로 저장된 파일 본문이 포함되지 않으며, 복구 시 삭제된 객체가 자동으로 돌아오지 않습니다. 대상 프로젝트의 실제 백업 가용성·보존 기간·PITR 설정·요금은 이번에 조회하거나 변경하지 않았습니다. [Supabase 백업 안내](https://supabase.com/docs/guides/platform/backups)

## 격리 백업·복원 연습

`npm run test:backup-recovery`는 `DAY12_PG_MODULE_ROOT`가 가리키는 저장소 외부의 고정된 `embedded-postgres@17.11.0-beta.19`와 `pg@8.23.1`을 이용합니다. 현재 스크립트는 **Windows x64 전용**이며, 새 임시 폴더와 임의의 localhost 포트만 사용합니다. 원격 DB 주소·기존 데이터 폴더를 입력받지 않습니다. 새 임시 로그인 비밀번호와 역할은 가상 테스트 전용이고 출력·저장소 기록을 하지 않습니다.

1. 빈 로컬 PostgreSQL 17 클러스터를 만들고 4·8~12·14~19일차 SQL을 순서대로 적용한 다음 가상 강좌·12주 내용·기수·신청·문의·이력·브랜드·파일 **메타데이터**를 만듭니다. SQL 이름과 해시는 테스트 전용 `fixture_meta`에 기록합니다. 이는 실제 Supabase 마이그레이션 이력이 아닙니다.
2. 테스트 연결을 닫고 `pg_ctl stop -m fast -w`로 원본 로컬 서버를 정상 종료한 뒤 전체 데이터 디렉터리를 백업 폴더로 복사합니다. 파일별 크기와 SHA-256을 원본과 대조합니다. 외부 경로를 가리키는 심볼릭 링크가 발견되면 중단합니다.
3. 백업을 별도로 복제해 테스트용 파일을 손상시키고 해시 불일치를 확인합니다. 불일치한 복사본을 DB 서버로 시작하지 않습니다. 해시 자체는 신뢰된 위치에 별도 보관·서명하지 않으므로 악의적 변조에 대한 완전한 보호를 의미하지 않습니다.
4. 백업 후 원본을 다시 열어 가상 신청을 한 건 추가합니다. 원본과 다른 폴더·포트에 백업을 복사하고 파일 해시를 확인한 뒤 복원 서버를 엽니다. 백업에 없던 나중 신청은 복원되지 않으며 원본 두 건은 유지되는지 확인합니다.
5. 복원본의 16개 테이블 데이터 지문·행 수, 테스트용 SQL 출처, RLS 활성화, 정책, 제약조건, 역할과 주요 함수·뷰 권한을 백업 직전과 비교합니다. 익명 역할의 공개 조회·비공개 신청정보 차단과 서비스 역할의 마스킹된 신청 확인도 시험합니다.
6. 테스트 서버를 정상 중지하고 경로와 서버 상태를 확인한 뒤 가상 데이터·백업·복원본을 포함한 임시 폴더만 삭제합니다. 서버 상태가 불확실하면 자동 삭제하지 않고 오류를 보고합니다.

최종 실행에서 별도 복원 폴더 복사 시작부터 해시·서버 시작·데이터 및 권한 검증까지 **5.4초**가 걸렸습니다. 최초 백업 생성과 정리 시간은 포함하지 않은 가상 로컬 데이터의 단일 측정이며 실제 서비스의 복구 시간이나 목표가 아닙니다.

이 검사는 로컬에서 서버를 중지하고 같은 버전의 PostgreSQL 전체 디렉터리를 복사하는 **물리 백업 연습**입니다. `pg_dump`, `pg_restore`, Supabase Dashboard 복원, PITR, 개별 테이블 복구나 온라인 백업은 시험하지 않았습니다. 현재 PC에서 `pg_dump`·`pg_restore`가 발견되지 않았고 Docker 엔진도 실행 중이 아니었습니다. 로컬 파일 해시·테스트용 SQL 출처는 실제 백업 암호화, 무결성 증명, 접근통제 및 보존 정책을 대신하지 않습니다. 테스트용 파일 메타데이터에 대응하는 Storage 파일은 만들지 않았습니다.

## 장애 대응 절차 초안

1. **상황 분리:** 장애 시각과 사용자 영향, 변경 직전 배포·마이그레이션·설정, 오류 범위를 확인합니다. 신청 결과가 불확실한 사용자가 중복 신청하지 않도록 처리 상태 확인 절차를 마련합니다. 로그·티켓에 비밀번호, 키, 신청자 이름·연락처·문의 본문을 복사하지 않습니다.
2. **확산 방지:** 담당자는 환경과 프로젝트 ID를 확인하고, 영향 받는 기능의 중지·복구 순서를 정합니다. 실제 기능 중지, 키 교체, 복원 또는 배포 변경은 영향과 권한을 확인하고 승인된 절차로 수행합니다. 이번 작업에서는 설정을 변경하지 않았습니다.
3. **복원점 판단:** 마지막으로 검증된 백업·시각·범위, 이후 데이터 손실 가능량, 개인정보 보존·삭제와 외부 시스템 연관성을 확인합니다. 백업 생성·복원 권한, 비용, 중단 시간 및 복원 대상 프로젝트는 실제 실행 전에 확인합니다. 원본 데이터 보존과 사후 대조 방법을 준비합니다.
4. **격리 복원과 비교:** 승인된 별도 테스트 대상으로 먼저 복원하고 스키마·마이그레이션 이력·행 수·신청 정원·이력, RLS·테이블/열 GRANT·함수·이벤트 트리거를 검증합니다. 실제 Supabase Auth 설정·계정·세션, Storage 객체와 버킷 정책, 환경변수·비밀키, 외부 서비스는 별도로 확인합니다. 실제 개인정보 사용 여부와 접근 범위도 별도 승인합니다.
5. **서비스 복귀:** 사이트 버전 롤백과 DB 복구는 별개입니다. 복구 시점 이후 신청·문의의 중복·누락을 대조하고 담당자가 승인한 뒤 단계적으로 기능을 복구합니다. 프런트엔드 배포를 되돌려도 DB와 Storage는 자동으로 이전 상태가 되지 않습니다.
6. **기록·개선:** 장애 원인, 실제 중단·손실 구간, 복구 검증 결과, 미해결 항목을 개인정보 없이 기록합니다. 백업 암호화·접근권한·보존·파기와 복원본 파기 절차를 함께 검토합니다.

Supabase의 실제 백업·복구 범위와 제약은 [백업 안내](https://supabase.com/docs/guides/platform/backups), [CLI 백업·복원 안내](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore), [새 프로젝트 복원 안내](https://supabase.com/docs/guides/platform/clone-project)를 실행 시 다시 확인해야 합니다. 프로젝트마다 사용 가능한 기능이 다를 수 있습니다.

## 미완료 항목

- 실제 개발 프로젝트의 백업 존재 여부, 요금제·PITR·보존 기간 및 복원 권한은 미확인입니다. 실제 백업 다운로드나 복원은 수행하지 않았습니다.
- 실제 Supabase DB 백업의 복원, 마이그레이션 이력, `public.rls_auto_enable()` / `ensure_rls`, Auth, Storage 파일·정책, Vercel 환경과 실제 통합 흐름은 시험하지 않았습니다. 기존 보안 경고 2건은 20일차 확인 당시 미해결이었습니다.
- 원격 개발 DB와 운영 DB, 다른 프로젝트, `main`, 기존 보안 마이그레이션 초안과 Vercel 운영 배포는 변경하지 않았습니다.
