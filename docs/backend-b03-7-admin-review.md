# B-03-7 관리자 화면·교육일정 연동 검수

검수일: 2026-11-10 (Asia/Seoul). 기준: PR #31 커밋 `69dd6f55b1cdf7191ef85d1b122639fc579c642f`. 개발 프로젝트: `uenvjqgylrevujdjpfed`.

## 판정

관리자 화면의 실제 읽기 및 권한 차단을 확인했고, 삭제 방안은 가상 데이터로만 실험했다. 실제 시험 기수의 삭제·수정·공개, DB 스키마·RLS·GRANT 변경은 수행하지 않았다. 이전 HTTP 500의 정확한 원인은 확인되지 않았다. 요청한 실제 Auth 로그인을 수행하면 Supabase Auth가 세션·로그인 메타데이터를 갱신할 수 있으므로 모든 관리 스키마가 바뀌지 않았다고 단정하지 않는다. 앱의 강좌·주차·시험 기수와 관리자 명단은 전후 조회 결과가 동일하다.

## HTTP 500 조사

- 2026-11-09 로컬 Next.js 개발 서버의 `GET /admin/console/offerings` 한 건은 `SyntaxError: Unexpected end of JSON input`과 HTTP 500으로 기록됐다. 해당 요청의 상세 스택과 실제 응답 본문은 보존되지 않아 원인·응답 상태가 Supabase에서 시작됐는지 알 수 없다. 이후 GET은 HTTP 200이었다.
- 화면은 서버의 `getAdminAccess()`가 실제 사용자·DB 관리자 여부를 확인한 뒤 `loadAdminOfferingCatalog()`를 호출한다. 관리자 확인과 목록 조회는 실제 Supabase 클라이언트와 RPC를 사용하며, 목록 조회 실패·잘못된 결과는 `null`로 처리하고 화면은 설정 확인 메시지를 표시하도록 작성돼 있다. Supabase 라이브러리·Next.js 내부의 JSON 처리까지 원인에서 배제할 수 없다.
- `scripts/verify-b03-7-json-failures.mjs`는 네트워크를 사용하지 않는다. 빈 JSON의 `Unexpected end of JSON input` 예외 자체를 만들고, 이를 가상 RPC·인증 실패로 주입해 목록 조회가 실패 상태를 반환하고 인증이 거부되는지 확인했다. 잘못된 응답 형태·가상 네트워크 실패·RPC 오류도 확인했다. **과거 실제 요청의 본문이나 HTTP 500을 재현한 것은 아니다.**
- 이번 실제 로컬 관리자 목록 GET은 HTTP 200이었고, 일반 사용자 로그인·관리자 접근 거부 및 API HTTP 403도 정상 응답했다. 이번 기본 빌드는 통과했다. 당시 HTTP 500은 재현되지 않았으므로 원인 미확정·미해결로 남긴다. 원인이 확인되지 않아 앱의 정상 기능은 수정하지 않았다.

## 시험 데이터 정리 방안 비교

현재 v2 함수와 전용 `academy_offering_executor`는 기수 조회·등록·수정만 다루며 DELETE 권한과 DELETE RLS 정책을 부여하지 않는다. 기존 관리자 로그인 자체가 삭제 권한을 부여하지 않는다.

| 방안 | 장점 | 위험과 현재 판단 |
| --- | --- | --- |
| 일회성 전용 정리 함수·전용 NOLOGIN/NOBYPASSRLS 역할 | 특정 개발용 UUID와 비공개 draft만 대상으로 제한하고 DB 관리자 확인을 재사용할 수 있음 | 함수·역할·GRANT·RLS 정책의 생성 및 종료 절차가 필요하다. 구현·권한이 잘못되면 삭제 권한이 넓어질 수 있으므로 실제 DB 적용 전 별도 승인·검증 필요 |
| 상시 관리자 삭제 기능 | 운영자가 추후에도 사용할 수 있음 | 신청·결제·출석·감사·복구·운영 정책이 미정인 상태에서 광범위한 삭제 기능은 부적절. 현재 구현·권한 추가 안 함 |
| postgres 등 고권한 직접 삭제 | 구현은 단순 | 기존 RLS 우회 금지·승인된 경로가 없으면 중단하라는 조건에 맞지 않아 사용하지 않음 |

`scripts/verify-b03-7-cleanup-design.mjs`는 **실제 UUID가 아닌 가상 UUID**와 PGlite 인메모리 DB를 사용하는 설계 실험이며 정식 SQL 마이그레이션이 아니다. 전용 역할은 NOLOGIN·NOBYPASSRLS이고 RLS 정책은 가상 UUID·draft·비공개에 한정한다. 가상 관리자·일반 사용자·익명·service 역할, 권한 회수 후 기존 가상 JWT, 잘못된 UUID, 기수 참조 FK 또는 신청·결제·출석·등록 테이블 존재 시 중단, 공개·비-draft, 지정 외 기수 보존 및 기존 강좌·주차 보존을 검증했다. 가상 관리자만 조건에 맞는 단일 기수를 제거할 수 있었다. 테이블 검사에 사용한 명칭은 예시이며 알려지지 않은 다른 이름의 참조는 탐지하지 못한다.

**실제 적용 준비 완료는 아니다.** PGlite는 Supabase 호스팅과 실제 PostgreSQL의 역할 부여·RLS·PostgREST·실제 JWT·동시 DDL/참조 생성 경합을 모두 증명하지 않는다. FK가 없더라도 외부 시스템·비 FK 참조를 증명하지 못한다. 실험에는 영구 감사·종료/권한 회수 메커니즘이 없다. 또 일반 데이터와 달리 테스트 기수임을 확증할 데이터 모델이 없으므로 UUID·상태만으로 운영용 기수 삭제를 일반화하면 안 된다.

실제 정리 검토 전에는 사용 목적과 담당자를 확정하고 최신 백업에 대상 행이 포함되는지와 복원 범위를 확인한다. 현재 검증된 백업은 기수 생성 전이므로 그 기수 자체를 포함하지 않으며, 최신 백업과 Auth 전체 복원은 미검증이다. 대상 UUID·정확한 행 내용·참조 및 이력 확인, 동시 변경 방지, 권한과 객체의 최소 범위, 함수 제거 또는 잠금, 실패·타임아웃 시 재시도 금지와 DB 조회, 복구 절차를 구체화한다. 실제 함수·역할·정책·권한 적용과 실제 삭제는 각각 검토 가능한 계획을 제시하고 별도 승인을 받는다.

## 검증

- `node scripts/verify-b03-7-json-failures.mjs`: 통과. 동일 유형의 JSON 오류 주입; 과거 HTTP 500은 미재현.
- `node scripts/verify-b03-7-cleanup-design.mjs`: 통과. PGlite 가상 정리 설계; 실제 DB 미적용.
- 관리자 인증·서비스·입력·폼·액션, B-03-6 PGlite 저장 및 v2 회귀 테스트 통과.
- PostgreSQL 17.11 격리 환경의 기존 v2 권한·저장·동시성 검사 통과. **신규 정리 실험 자체의 PostgreSQL 17.11 또는 Supabase 호환성은 별도 미검증.**
- ESLint·TypeScript 통과. 기본 `npm run build`는 개발 DB 정보가 없는 별도 물리 복사본에서 Turbopack으로 통과.
- 실제 로그인에서 테스트 계정 정보·토큰과 키는 기록하지 않았다. 개발용 웹 서버는 별도 로컬 포트를 사용했고 이후 정리한다.
