## 승인된 후에만 실행

1. A1은 독립 트랜잭션으로 한 번 실행한다. psql 등 실행기는 ON_ERROR_STOP을 사용하고 오류 시 중지·롤백한다. SQL 파일은 이미 BEGIN/COMMIT을 포함하므로 무심코 중첩하지 않는다.
2. 새 3개 테이블의 owner/RLS/ACL·기존 보안 지문·통제 행 phase=schema_only를 확인한다.
3. A2를 독립 트랜잭션으로 실행한다. timeout·충돌·데이터/권한 drift 발생 시 중단하고 원인을 보고한다.
4. A2 완료 후 기준선·신규 데이터와 공개 읽기 경계를 확인한다. 임의로 B/C를 이어서 실행하지 않는다.
5. 실행 결과·SQL 해시·영향 건수·미확정 항목·복구 가능성을 보고한다.

## B/C를 위한 추가 승인·검수

- B: 신규 6개 공개 승인, DB 기반 상세 화면의 초안 표시·시간 미확정·메타데이터 조회 계약·모바일 검수 필요.
- 신규 profile/practice 공개 또는 관리자 조회를 위한 별도 제한된 API/정책/권한 설계 필요. 이번 SQL에는 권한 확대가 없다.
- C_keep: 기존 공개 유지 기본안. 신규 공개 이후 목록은 11개가 된다.
- C_archive: 기존 URL 종료/이관 안내 구현·검수와 별도 공개 해제 승인 필요. 현재 사이트에 이 기능을 구현하지 않았으므로 실행 대상에서 제외한다.
- academy.ai_fusion_legacy_url_policy 문자열 설정만으로 이 승인·검수를 대신하지 않는다.
- 교육과정 review_state 전환·개정 등록은 별도 버전/승인 작업이며 이번 B에서 reviewed로 간주하지 않는다.

## 실패 및 복구

- A1 실패: 새 객체 전체 자동 롤백. 기존 데이터 유지.
- A2 실패: A2 전체 자동 롤백. A1 스키마와 schema_only 통제 행은 남는다. 원인 분석 없이 A1 재실행이나 객체 삭제를 하지 않는다.
- A2 재실행: 스냅샷·매니페스트가 정확히 일치할 때만 검증된 no-op를 허용한다.
- B/C 커밋 후 복구: D 후보가 기존 공개 상태 복원·신규 draft 복귀를 수행한다. 신규 행은 삭제하지 않는다.
- 데이터·권한 변화 또는 신규 기수 참조가 있으면 D도 거부한다. 과거 값을 강제로 덮어쓰지 말고 최신 상태 기반 복구안을 승인받는다.
- Supabase 고유 트리거/확장·네트워크/연결 단절·실환경 권한의 차이는 적용 후 별도 확인해야 한다.

main 병합과 Production 배포는 이 절차에서도 별도 최종 승인 대상이다.
