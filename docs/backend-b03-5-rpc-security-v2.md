## 권한 구조와 실제 경계

v1은 서비스 역할에 테이블 INSERT·UPDATE 권한을 주기 때문에 RPC의 검증을 우회할 수 있다. 격리 테스트에서 재현해 미적용 v1을 migration 경로에서 `supabase/drafts/b03_5_insecure_v1_do_not_apply.sql`로 이동했다. 이력에 기록된 4개 마이그레이션은 변경하지 않았다.

검토용 `supabase/drafts/b03_5_offering_rpc_security_v2.sql`은 다음을 제안한다.

1. 인증된 사용자의 JWT를 사용하는 서버 클라이언트와 기존 `getUser()`·서버 전용 ID 허용목록을 유지한다. 기수 경로는 서비스 비밀 키를 사용하지 않고 v2 RPC를 부른다. 강좌 관리의 기존 클라이언트는 변경하지 않는다.
2. `private_education`에 관리자 ID 목록과 helper를 둔다. helper는 `SECURITY DEFINER`, 빈 `search_path`, 스키마가 명시된 이름 및 `auth.uid()` 관리자 목록 확인을 사용한다. 공개 RPC는 `SECURITY INVOKER`이고 익명·서비스 역할의 EXECUTE는 회수한다.
3. helper 소유자는 로그인·BYPASSRLS·역할 생성 권한이 없는 전용 역할이다. 해당 역할에 필요한 열 권한과 역할 전용 RLS만 부여한다. 인증 사용자와 서비스 역할은 역할의 멤버가 아니며 기수 테이블 직접 쓰기 권한을 받지 않는다.
4. 모집기간 누락·역전, 정원 음수 및 모집중 0, 비공개 강좌의 공개 기수, 공개 draft, 중복 입력을 거부한다. 동일 내용 동시 등록은 트랜잭션 잠금으로 직렬화한다. 중복 기준은 모든 일정 속성이 같은 경우다.
5. 신청 테이블이 존재하면 저장을 중단한다. **실제 신청자 수에 따른 정원 초과 방지는 아직 구현하지 않았다.** 신청 기능이 생기기 전 잠금 순서·정원 축소·신청 동시성 검토가 필요하다.

### 반드시 해결할 적용 전 위험

- **서버 허용목록과 DB 목록의 불일치:** DB 목록에 남아 있는 관리자는 서버 환경변수에서 제거됐어도 유효한 본인 JWT로 Data API의 v2 RPC를 직접 호출할 수 있다. 서버 검사는 이 직접 호출을 중재하지 못한다. 관리자 등록·회수의 단일 기준과 양쪽 동기화, 세션 만료·회수 정책을 결정하고 실제 비관리자 JWT로 검증해야 한다. 이 후보를 서버 허용목록만으로 보호된 구조라고 보고하지 않는다.
- DB 관리자 목록은 빈 상태로 생성된다. 실제 관리자 등록 SQL은 포함하지 않았다. 사용자 ID 등록, 회수 및 변경 권한은 별도 승인 대상이다.
- 역할 생성·역할 membership·함수 소유권 이전과 기존 기본 ACL, `ensure_rls` 트리거, PostgREST 노출 범위가 실제 호스팅 프로젝트에서 동작하는지 **미검증**이다. `postgres`는 해당 개발 DB에서 `CREATEROLE`이나 슈퍼유저는 아니다. 격리 DB의 슈퍼유저 성공을 호스팅 적용 가능 증거로 사용하지 않는다.
- 실제 Supabase JWT·PostgREST를 통한 v2 RPC, admin 등록·수정, 별도 일반 사용자, Data API 권한 및 Security Advisor 적용 후 결과는 미검증이다. 격리 테스트의 `auth.uid()`는 가상 요청값이므로 실제 JWT 서명을 검증하지 않는다.
- v1이 과거 어느 DB에 이미 적용됐다면 이 v2 초안의 사전 검사는 중단한다. 기존 권한을 무조건 회수하거나 DB를 초기화하지 않는다. 실제 이력·함수·ACL 및 단일 대상 dry-run을 다시 확인하고 복구안을 검토한다.
- 역할 생성과 함수 소유자 변경은 데이터베이스 차원의 보안 변경이다. 실행 시 단일 트랜잭션과 잠금·오류 발생 시 롤백·마이그레이션 기록의 원자성을 검증해야 한다. 실패·타임아웃 시 재실행하지 말고 이력·객체·권한을 조회한다.

## 검증과 남은 항목

- 격리 PostgreSQL 17.11: 서비스 역할 직접 INSERT·UPDATE 거부, 일반 사용자·목록에서 제거한 사용자 거부, 전용 역할 속성과 비멤버십, 관리자 가상 등록·수정, 입력 오류·동일 내용 중복, 공개 뷰, 신청 테이블 가드, 동시 중복 잠금 확인. 임시 DB만 사용했다.
- 기존 실제 로그인 세션은 보안 브랜치의 관리자 콘솔에서 허용됐다. 관리자 기수 기능은 비활성 상태로 안전하게 중단됐다. 실제 v2 저장은 하지 않았다. PC 및 모바일에서 홈·관리자 콘솔을 확인했다.
- 기본 빌드, TypeScript·ESLint, 인증과 관리자·공개 회귀 테스트의 결과는 PR 설명을 기준으로 한다.
- `npm audit`은 중간 8건이며 `minimatch`의 glob 확장에 따른 서비스 거부 경고가 `typescript-eslint` 및 `eslint-config-next` 개발 도구 의존성으로 전파됐다. 신뢰할 수 없는 저장소나 glob 입력을 CI lint에서 처리할 때 자원 고갈 위험이 있다. `npm audit --omit=dev`에서는 0건이다. 이것이 전체 런타임 보안 보증은 아니다. npm이 제안한 메이저 변경은 Next 설정 버전을 바꾸므로 자동 적용하지 않았다. [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249)
