# B-03-4: 공개 기수·일정 연결 준비

기준은 PR #26 HEAD `056430af9afd5123487f7c89fe6acd26c0a27376`, 대상은 개발 프로젝트 `ai-education-hub-dev` / `uenvjqgylrevujdjpfed`다. 2026-11-08 조회 시 강좌 5개·60주, 기수 0건이며 강좌·주차 전체 행 해시는 B-03-3 검수 시점과 같다. 공개 강좌·주차의 실제 익명 GET은 각각 5건·60건, 일정 뷰는 아직 없어 404 / `PGRST205`였다. 이번 작업에서는 개발 DB를 변경하지 않았다.

## 일정 공개 마이그레이션 후보

`supabase/migrations/20261108143123_public_offerings_catalog.sql`은 CLI 3.0.0으로 만든 **미적용 후보**다. 정규화 SHA-256(UTF-8 CRLF→LF, 양끝 공백 제거)은 `22819a03eb0d4444e89c60b6f74d5adf3de528947e534a590c84206151fc20c4`이다. 실제 적용 이력은 아니며 runner가 다른 버전을 기록한다면 이력 확인 후 파일명·참조를 동기화하고 SQL은 재실행하지 않는다.

| 대상 | 후보 변경 |
| --- | --- |
| `academy.offerings` | `is_public boolean NOT NULL DEFAULT false` 추가. 기존 모집 상태 `status`와 분리 |
| 정책 | `offerings_select_public`: 공개 지정, 작성 중 아님, 부모 강좌 공개인 행만 `anon`·`authenticated`가 조회 |
| 열 권한 | 두 역할에 공개에 필요한 ID·일정·모집 시작/종료·장소·정원·상태·공개 여부 SELECT만 부여. 쓰기 권한 없음 |
| `public.published_offerings` | `security_invoker=true`, 공개 기수와 공개 강좌 JOIN. 기존 일정 클라이언트 열 유지, 모집 시각 두 열 추가 |
| 뷰 ACL | 새 뷰에서 `PUBLIC`, `anon`, `authenticated`, `service_role`의 기본 권한을 회수한 뒤 두 공개 역할에 SELECT만 부여. 전체 기본 ACL은 변경하지 않음 |

9일차 초안과 달리 모집 시각 두 열도 공개 일정 정보로 노출하고, 실제 관찰된 `public` 기본 ACL에서 새 뷰에 불필요하게 주어질 수 있는 `service_role` 권한을 해당 뷰에 한해 제거한다. `academy`가 Data API에 노출되면 뷰뿐 아니라 기초 테이블의 허용된 열도 RLS를 거쳐 접근 가능하므로, 스키마 노출 설정도 실제 적용 후 확인해야 한다. 이후 서비스 역할이 새 뷰를 직접 사용할 필요가 생기면 별도 설계가 필요하다.

후보 사전 검사는 실행 역할·소유자·RLS·필요한 공개 강좌 열 권한, 같은 열/뷰/정책, 예상 밖 기수 권한·기본 뷰 ACL을 확인한다. `academy.offerings` 잠금 후 빈 상태도 확인한다. 잠금이 후속 DDL까지 유지되도록 **검증된 단일 트랜잭션 실행기**가 필요하다. 예상 밖 객체·데이터·권한이면 중단한다. 기존 강좌 정책·뷰·데이터는 수정하지 않는다.

기존 `day09_dev_offerings.sql`은 별도 개발용 예시이며 후보에 포함하지 않고 실제 DB에 실행하지 않았다. 해당 초안의 모집 시각은 모두 NULL이므로 `open` 상태만으로 실제 신청이 가능하다고 표시하거나 해석해서는 안 된다. 예시 데이터 등록에는 별도 검토·승인이 필요하다.

## 모집 시각과 실제 신청

- 관리자 입력과 표시는 `Asia/Seoul` 기준으로 설계한다. `datetime-local`을 서버 실행 환경의 시간대로 해석하지 말고 한국 시간임을 명확히 표시해 해당 시각을 오프셋이 있는 절대 시각으로 변환한다. DB에는 이미 존재하는 `timestamptz` 두 열을 사용한다. [PostgreSQL 시간대 자료형](https://www.postgresql.org/docs/17/datatype-datetime.html)
- 시작 시각은 포함, 종료 시각은 제외한다. 두 값 중 하나라도 미정, 잘못된 값, 동일하거나 역전된 값, 기간 밖, 비공개 기수·강좌 또는 `open`이 아닌 상태는 **신규 신청 불허**다. 실제 접수에서는 정원 및 중복 검사도 DB 트랜잭션 안에서 다시 확인해야 한다.
- 기존 `academy.offerings`의 CHECK는 두 시각이 같거나 한쪽이 NULL인 저장을 허용한다. 이는 해당 기수를 **접수 가능**하게 만든다는 뜻이 아니다. 저장 정책 강화·기존 데이터 처리와 DB 제약 변경은 이번 후보에 포함하지 않는다.
- 기존 `validateApplicationRequest` 검증 함수는 NULL·역전·경계 시간을 거부했지만 JavaScript 날짜 보정으로 실제로 없는 날짜를 통과시킬 수 있었다. `src/lib/applications/validation.ts`에서 달력 날짜·시/분/초를 엄격히 확인하도록 보완하고 잘못된 날짜·동일 시각에 대한 회귀 검사를 추가했다. **이 함수는 현재 `submitApplication`에 연결되어 있지 않고 실제 신청 어댑터나 공개 경로도 없다.** 실제 구현 시 기존 요청의 안전한 재시도와 충돌하지 않도록 사전 검증 및 DB 최종 판단 순서를 설계해야 한다. 사전 검증은 예약·DB 트랜잭션을 대체하지 않는다.
- 12일차 신청 SQL 초안도 양쪽 시각과 `start <= now < end`를 확인하지만 실제 DB에는 아직 적용되지 않았다. 실제 접수는 서버·DB 양쪽에서 동일한 실패 차단 규칙을 확인하고 동시성·정원 테스트 및 별도 승인 후에만 연결한다.

## 관리자 저장 누락 해결 계획

현재 관리자 양식·타입·검증·RPC 호출 및 `day10_admin_management.sql`, `day12_atomic_applications.sql`의 저장 함수는 두 모집 시각을 전달·저장하지 않는다. 현재 관리자 RPC는 실제 개발 DB에 존재하지 않는다. 이번 공개 뷰 후보는 관리자 함수나 `service_role` 권한을 추가하지 않으며, 관리자 화면의 모집 시각 저장도 **아직 구현되지 않았다**.

후속에서는 버전이 명확히 구분된 새 저장 RPC의 두 `timestamptz` 인수와 관리자 폼·타입·서버 검증·조회 결과를 함께 준비한다. 공개 여부와 모집 상태는 별도 필드로 유지한다. 신청이 존재하는 기수의 강좌 변경 금지·정원 축소 금지·행 잠금 순서를 최종 day12 구현에서 유지하고, 서비스 전용 최소 권한과 관리자 인증 경계를 격리 검증한다. 구 함수와 새 함수가 동시에 동작하는 배포 기간의 우회·권한 회수·롤백을 별도로 검토한다. 실제 DB 적용은 별도 승인 대상이다. 공개 화면의 현재 `모집중` 문구는 저장된 상태 표시이며, 시간·정원에 대한 실접수 가능 여부 표시로 사용하지 않도록 후속 화면 계약을 정해야 한다.

- `npm run test:public-offerings-migration`: 격리 PGlite에서 실제 기초·공개 강좌 후보와 가상 5강좌·60주를 구성해 공개/비공개 강좌·기수, draft, invoker 뷰, 역할별 조회·쓰기 거부, KST 오프셋, 날짜·정원 제약 및 기존 권한·기수·뷰 충돌 중단을 확인했다. 실제 Supabase가 아니다.
- `npm run test:application-validation`: 시작 포함·종료 제외, 미정·동일·역전·존재하지 않는 날짜의 신규 신청 거부 통과.
- 기존 일정 접근, 강좌 서비스, 관리자 입력, 신청 스키마 격리 검사 통과. 실제 관리자 계정/JWT·일정 API·신청 SQL 및 실제 쓰기 흐름은 미검증이다.
- `npx tsc --noEmit`, 경고 0개 ESLint 통과.

## 기본 빌드 진단

기본 `npm run build`는 Next.js 16.4.5 Turbopack이 CSS loader 처리 중 Node 자식 프로세스에 연결하기 전에 종료됐다고 보고한다. 일반 Node 24.20.0과 별도 Node 24.22.1에서 재현됐다. 현재 `next.config.ts`는 `@tailwindcss/turbopack` CSS loader를 지정한다. 이것이 문제 경로이지만 실패의 근본 원인은 확정되지 않았다.

`npx next build --webpack`은 종료 코드 0이었지만 생성 CSS에 실제 사용 중인 `.w-full`, `.p-5`, `.bg-brand-navy` 유틸리티가 없고 `@theme` 규칙이 남아 있었다. 따라서 Webpack 종료 성공만으로 화면이 정상이라는 근거가 되지 않으며 운영 전환 대안으로 승인할 수 없다.

최소 수정 후보는 별도 격리 작업에서 Next.js가 문서화한 `@tailwindcss/postcss` 설정을 검토하고 기존 Turbopack 전용 loader와 충돌하지 않게 구성하는 것이다. 의존성·설정 변경 전후 기본 및 Webpack 빌드, 생성된 실제 유틸리티 CSS와 주요 화면의 시각·반응형 회귀를 비교해야 한다. 이 후보는 아직 적용·검증하지 않았고 현재 PR에서 빌드 구성을 임의 수정하지 않았다. Node 24.13.1 이상에서 강제 worker thread는 Next.js 문서상 종료 위험이 있어 임시 우회로 채택하지 않는다.

## 실제 적용 전 승인·실패 복구

적용 전 프로젝트 ID, 후보 해시, 기존 이력 3건과 실제 스키마·권한·기수 0건, 강좌 5개·60주 및 백업을 다시 확인한다. 단일 트랜잭션을 보장하는 실행 경로와 dry-run에서 후보 1건만 적용 대상으로 나오는지 확인한다. 예상 밖 대상 또는 실패 시 추가 변경을 멈추고 이력·객체·권한을 읽기 전용으로 확인한다. 부분 적용이나 타임아웃 시 재실행하지 않는다. 실제 적용 후 문제가 있으면 기존 데이터와 후속 의존성을 보존하면서 별도 승인된 복구 또는 정방향 수정 계획을 사용한다. 공개 뷰·정책·열을 자동 삭제하지 않는다.

실제 스키마 변경, 가상 기수 등록, 관리자 함수 변경, 다른 프로젝트·운영 DB·main·Vercel Production 변경은 하지 않았다.
