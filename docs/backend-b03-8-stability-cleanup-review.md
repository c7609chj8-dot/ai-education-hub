# B-03-8 관리자 안정화·시험 기수 정리 준비

점검일: 2026-11-10 (Asia/Seoul). 기준: PR #32, 커밋 `5172deabf8b2887d5bf8cc92e891220ad3d7c9b4`. 실제 대상: 개발 프로젝트 `uenvjqgylrevujdjpfed`.

## 판정

관리자 목록 실패를 기존처럼 접근 차단·안전한 빈 상태로 처리하면서, 서버 로그에 정해진 단계와 오류 분류만 남기도록 보완했다. 이전 HTTP 500은 상세 스택·응답 본문이 없고 이번에도 재현되지 않아 원인은 **미확정·미해결**이다. 시험 기수 삭제는 실행하지 않았고 실제 삭제 경로도 만들지 않았다.

## HTTP 500과 진단

- 기존 로그는 로컬 `GET /admin/console/offerings`의 `SyntaxError: Unexpected end of JSON input`과 HTTP 500만 확인됐다. 요청의 실제 본문과 예외 발생 지점은 남지 않았다.
- 호출 경로는 Next 프록시의 인증 갱신 → `getAdminAccess()`의 실제 사용자와 DB 관리자 여부 확인 → 사용자 세션의 `academy_admin_offerings_catalog_v2` RPC → 데이터 형태 확인 → 화면이다. 이 경로의 응용 코드에는 해당 JSON 파싱을 직접 수행하는 부분이 없지만 Next·Supabase 라이브러리의 내부 원인은 배제할 수 없다.
- 기존 2.119.0 계열의 설치된 PostgREST 클라이언트 코드를 점검했다. 가상 fetch로 실클라이언트를 시험한 결과 200 빈 본문은 데이터 없음으로, 200 잘못된 JSON은 오류로 반환됐다. 관리자 목록은 둘 다 안전하게 실패 처리한다. 예외·응답 상태로 파싱 오류, 잘못된 응답, 인증 오류, 시간 초과, 요청 제한, 서버 5xx, 네트워크 또는 클라이언트 오류, 미확인을 구분하되 정보가 부족한 경우 원인을 단정하지 않는다. 인증 오류는 반드시 만료만을 뜻하지 않으며 TypeError도 항상 네트워크 오류를 뜻하지 않는다.
- `admin_diagnostic` 로그는 고정된 단계·분류 두 값만 기록한다. 오류 메시지·본문·URL·헤더·사용자 ID·JWT·키는 기록하지 않는다. 가상 오류에 비밀 표식이 포함돼도 로그에 나타나지 않는지 시험했다. 정상적인 비관리자 판정은 관리자 권한을 주지 않는다.
- 빈 JSON 오류의 유형은 격리 주입으로 재현했고 실제 SDK의 가상 응답도 시험했다. **과거 HTTP 500 자체와 발생 위치는 재현하지 못했으며, 이번 변경이 당시 오류를 해결했다고 주장하지 않는다.**

## 삭제 설계와 참조 확인

현재 관리자 v2는 조회·등록·수정만 제공하며 인증·익명·service 역할에 기수 테이블 DELETE를 부여하지 않는다. 읽기 전용 조회에서 대상 기수에 대한 외래키는 없고, academy/public/private_education 테이블에 offering·cohort·schedule 이름의 열은 없었다. 미적용 신청 SQL 초안에는 기수를 참조하는 FK가 있으므로 향후 적용 시 정리 조건이 달라진다. 외부 서비스와 다른 이름·JSON 등의 비 FK 참조 부재는 증명하지 못했다.

정리 목적은 **개발용 UUID 한 건**이며 상시 관리자 삭제 기능과 구분한다. 권장 검토 방식은 기존 관리자 v2를 수정하지 않는 일회성 전용 NOLOGIN·NOBYPASSRLS 역할과 제한된 함수다. 새 역할에 대상 테이블의 필요한 SELECT 열 및 DELETE를 주더라도, 별도 RLS 정책과 함수 내부 조건이 고정 UUID·비공개 draft·기대 장소로 제한해야 한다. 기존 인증 사용자는 테이블을 직접 삭제하지 못하고, 함수는 기존 DB 관리자 목록을 매 호출 확인해야 한다. 공개 래퍼와 비공개 함수의 EXECUTE, 역할 멤버십, 검색 경로, RLS 정책의 OR 결합, 함수·정책·역할 회수 및 감사 기록을 별도로 검토해야 한다. **이는 권한 변경이 수반되는 설계 실험이지 승인된 실행 경로가 아니다.**

`scripts/verify-b03-8-cleanup-postgres-cases.mjs`는 실제 UUID 대신 가상 UUID를 사용해 격리 PostgreSQL 17.11에서 전용 역할, 관리자·일반·익명·service 구분, 잘못된 ID·기대 장소 불일치, 참조 FK 존재 시 중단, 단일 삭제와 롤백을 시험했다. 다른 트랜잭션이 기수를 draft가 아닌 상태로 먼저 변경하는 경합에서 잠금 대기 후 조건을 재검사해 삭제하지 않았다. 가상 행 전체를 별도 롤백 전용 트랜잭션에서 복원하고 내용이 같은지도 확인했다. 이 복원은 격리 DB 소유자 권한만을 사용한 실험이며 실제 Supabase 복원 경로가 아니다.

호스팅 DB의 postgres는 비슈퍼유저 CREATEROLE·BYPASSRLS이며 기존 전용 기수 역할은 NOLOGIN·NOBYPASSRLS임을 읽기 전용으로 확인했다. **신규 역할 생성·소유권 이전·실제 JWT/PostgREST 경로·정책 적용과 회수는 실제 호스팅에서 미검증**이다. 격리 테스트는 동시 행 변경을 다뤘지만 동시 DDL, 새로운 FK·비 FK·외부 서비스 참조의 생성 경쟁까지 보장하지 않는다. 미지의 참조는 보수적으로 중단해야 한다.

## 백업·복구

- 기존 전체 수동 백업 4개 파일의 SHA-256이 일치했다. 해당 백업은 시험 기수 등록 전으로 기수 0건이며 최신 Auth 전체 복원 시험은 미실시다.
- 이번에 현재 시험 기수 **한 행만** 읽어 사용자·SYSTEM으로 접근이 제한된 기존 백업 루트 아래 `b038-test-offering-snapshot-20261110-222128`에 JSON과 SHA-256 목록을 저장했다. 파일 해시가 일치하고 실제 DB의 해당 행 11개 열과 같음을 확인했다. 행 단위 스냅샷은 DB 전체·Auth·Storage 백업이 아니다.
- 복구가 필요하면 먼저 DB 현재 상태와 참조·스냅샷 해시를 확인하고 중복 UUID·기존 강좌를 대조한다. 전체 DB를 덮어쓰지 않으며, 실제 단일 행 복원에 사용할 최소 권한 경로와 SQL은 별도로 검토·승인해야 한다. 실제 Supabase에서 행 복원은 시험하지 않았다.

## 검증 결과

- 실제 관리자 화면·일반 사용자 403·미인증 401·익명 공개 API 확인.
- JSON/네트워크/인증/5xx/429 오류 주입, 실제 설치된 PostgREST 파서의 가상 빈·잘못된 응답 및 로그 비노출 테스트 통과.
- PostgreSQL 17.11 격리 클러스터의 기존 v2 권한·동시성, 가상 정리의 오류·롤백·행 경합과 가상 한 행 복원 통과. 최초 격리 실험은 테스트의 DDL과 BEGIN이 같은 배치에 있어 롤백이 테스트 테이블 삭제를 되돌리는 문제가 드러났고, 트랜잭션 경계를 분리해 재실행해 통과했다.
- TypeScript·ESLint·기본 Next.js Turbopack 빌드, 관리자 인증·기수 서비스·기존 회귀 테스트 통과. 빌드는 실제 개발 DB 자격 증명이 없는 별도 물리 복사본에서 수행했다.

## 실제 변경에 앞선 승인 단계

현재 검증물은 **가상 fixture**이며 실제 개발 DB에 적용할 정식 SQL과 외부 참조·동시 DDL 대응, 감사·전용 권한 회수 계획이 아직 완성되지 않았다. 따라서 지금 승인만으로 실행할 수 있는 안전한 삭제 계획으로 간주하지 않는다. 다음 작업에서 정확한 개발용 SQL·버전·대상·권한 변화·실패 복구·수명 종료 절차를 검토 가능한 형태로 준비하고 실제 호스팅에서 가능한 읽기 전용 사전 확인을 한 뒤, **역할/함수/정책 적용과 기수 한 건 삭제를 각각 별도로 승인**받는다. 실제 삭제 전에는 백업과 대상 행·참조·세션을 다시 확인하고, 오류·타임아웃이면 재실행하지 않고 상태를 조회한다.

main 병합, 운영 배포, 다른 Supabase 프로젝트 변경, 실제 기수 삭제·수정·공개 및 실제 RLS·GRANT 변경은 하지 않았다.
