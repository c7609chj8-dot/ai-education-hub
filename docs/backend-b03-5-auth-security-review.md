# B-03-5 Auth·서비스 권한 재검수

점검일: 2026-11-09 (Asia/Seoul). 개발 프로젝트 `ai-education-hub-dev` / `uenvjqgylrevujdjpfed`만 읽기 전용으로 확인했다. 관리자 RPC 적용은 보류 중이며 이 문서는 적용 승인이 아니다.

## 실제 로그인과 관리자 ID

- 계정 생성 직후 두 차례 조회에서는 `auth.users`가 0건이었으나, 이후 같은 개발 프로젝트에서 테스트 계정 1건을 확인했다. 실제 로그인과 허용목록 포함·미포함에 따른 접근 차단은 별도로 검증해야 한다. 이메일·비밀번호·토큰을 문서에 기록하지 않는다.
- 코드의 `getVerifiedUser()`는 서버에서 Supabase Auth의 `getUser()` 결과를 확인한다. `getAdminIdentity()`는 그 사용자 ID와 서버 전용 `ACADEMY_ADMIN_USER_IDS`를 비교한다. 비어 있거나 잘못된 목록은 실패 차단되며 사용자 메타데이터는 관리자 권한에 사용하지 않는다. 서버 액션과 특권 클라이언트는 각각 관리자 접근을 확인한다.
- `npm run test:admin-auth-gates`의 가짜 Auth 응답으로 미인증 401, 허용목록에 없는 사용자 403, 목록에 든 사용자 200, 오류·위조 메타데이터·잘못된 목록의 실패 차단을 확인했다. 이는 실제 로그인 결과가 아니다. 기존 서비스·액션 모의 검사도 통과했다.
- 로컬 Webpack 서버의 비인증 `/api/admin/access`는 401이고 관리자 기수 페이지는 로그인으로 307이었다. 실제 Supabase 로그인이나 인증된 사용자에 대한 검사는 아니다.

### 실제 로그인 검증 절차 — 아직 실행하지 않음

1. 대시보드에서 프로젝트 ID가 정확히 `uenvjqgylrevujdjpfed`인지 확인하고 **Authentication → Users**에 개발용 테스트 계정이 표시되는지 확인한다. 일반 사용자 차단과 관리자 허용을 구분하려면 두 계정을 사용하거나 같은 계정에 대해 허용목록 비포함·포함을 나누어 시험한다. [Supabase 사용자 안내](https://supabase.com/docs/guides/auth/users)
2. 로컬 개발 서버에 개발 프로젝트 URL과 **publishable** 키를 설정한다. `ACADEMY_ADMIN_USER_IDS`는 서버 전용 변수이며 클라이언트에 노출되는 접두사를 붙이지 않는다. 첫 시험은 목록을 비워 둔다. `SUPABASE_SECRET_KEY`를 제공하지 않고 관리자 저장 기능도 활성화하지 않는다. 비밀번호·토큰·키는 채팅이나 Git에 넣지 않는다.
3. 사용자가 로컬 로그인 화면에서 비밀번호를 직접 입력한다. 로그인 후 목록 미포함 계정의 `/api/admin/access`는 403 / `authorized:false`여야 한다. 401이면 로그인 또는 세션부터 실패한 것이므로 일반 사용자 차단 성공으로 기록하지 않는다.
4. 서버를 중지하고 개발용 사용자 ID만 서버 전용 허용목록에 설정한 뒤 같은 로컬 주소로 재시작한다. 서버 검증 세션에 대한 `/api/admin/access`는 200 / `authorized:true`여야 한다. 로그아웃 후에는 401을 확인한다. 계정 전환 시 브라우저 세션을 분리하고 ID·토큰을 로그에 기록하지 않는다.
5. 위 시험은 관리자 접근 판단만 검증한다. RPC는 아직 적용되지 않아 실제 저장이 되지 않는다. 기본 빌드 오류로 정상 UI/CSS는 미검증이며, `next dev --webpack`도 시각적 정상성을 보장하지 않는다.

## 브라우저 키 노출 점검

- `SUPABASE_SECRET_KEY`·`ACADEMY_ADMIN_USER_IDS`를 읽는 소스 8개 모두 `server-only` 모듈이며, 관리자 서버 액션도 매 요청 접근을 확인한다. 이는 소스 범위의 결과다.
- 가짜 서비스 키와 가짜 관리자 ID를 서버 환경에 넣은 로컬 Webpack 빌드의 `.next/static` 57개 파일을 검사한 결과, 가짜 값과 두 서버 환경변수 이름은 발견되지 않았다. 가짜 값으로 실행한 로컬 공개·로그인·비인증 관리자 API 응답에서도 두 값이 발견되지 않았다.
- Vercel에서 조회된 `ai-education-hub` 프로젝트의 프로젝트 단위 환경변수 목록은 0건이었다(값 복호화 없음). 공유 환경변수와 실제 배포된 모든 응답·인증 세션은 검사하지 못했으며, 이 결과만으로 실제 비밀의 비노출을 완전히 증명하지 않는다.

## 실제 DB와 후보 SQL 차이

현재 실제 개발 DB는 마이그레이션 4건, 강좌 5개·60주, 기수 0개이고 관리자 함수는 없다. `academy.courses`와 `academy.offerings`의 RLS가 활성화돼 있으며 기존 공개 정책·invoker 뷰가 유지된다. `anon`·`authenticated`에는 기수 쓰기 권한이 없고, 현재 `service_role`에도 `academy` USAGE 또는 기수 쓰기 권한이 없다. 신청 테이블과 충돌 관리자 함수도 없다. 계정 생성 이후 Security Advisor에 유출 비밀번호 보호가 비활성화된 `auth_leaked_password_protection` WARN 1건이 표시됐다. 설정은 변경하지 않았으며 별도 검토가 필요하다.

미적용 `20261108162624_admin_offering_management.sql`의 정규화 SHA-256은 `16de60a8b7c67dc91f063bbcff0bc2b0813850d0a4f295af34c9e769e69925ab`로 검토 후보와 같다. 이 후보는 invoker 함수 2개, 서비스 역할의 `academy` USAGE, 강좌 3개 열 SELECT와 기수 지정 열 SELECT·INSERT·UPDATE를 제안한다. 익명·인증 역할의 함수 EXECUTE는 막는다. 사용자별 관리자 인가는 DB가 아니라 서버에서 수행된다.

### 확인된 직접 쓰기 우회

`npm run test:admin-offering-privilege-boundary`는 **격리 PGlite**에서 후보를 적용하고 동일한 가상 입력을 비교했다. 모집기간이 없는 공개·모집중 기수는 RPC가 `Invalid offering`으로 거부했지만, 제안된 서비스 역할 열 권한을 이용해 테이블에 직접 INSERT하면 저장됐고 익명 공개 뷰에서도 조회됐다. 실제 DB에 시험 데이터를 넣지 않았다. `service_role`은 RLS도 우회하므로 이 후보는 특정 열로 범위를 좁혔어도 RPC 사용을 강제하지 못한다. 기존 감사·중복·기간 검증과 미래 신청 테이블 가드도 직접 쓰기로 우회할 수 있다. 정상 서버에서 키를 보호하고 인증을 수행하는 것과 이 위험이 없다는 것은 다르다.

**현재 후보를 RPC만으로 제한된 권한이라고 부를 수 없다.** 우선 적용을 보류하고 다음 대안을 별도 SQL·격리 검증으로 비교한다.

1. 현재 invoker 설계를 유지한다면 서비스 키 보유 서버의 직접 테이블 쓰기 능력을 명시적으로 받아들이고 모든 키 사용처와 비밀 유출 대응을 검토한다.
2. 전용 NOLOGIN 소유 역할에 필요한 테이블 권한과 해당 역할용 RLS 정책을 제한하고, 고정 `search_path`·입력 검증을 갖춘 별도의 `SECURITY DEFINER` RPC에 서비스 역할의 EXECUTE만 허용하는 방안을 검토한다. 함수 소유·역할 상속·PUBLIC 권한과 RLS, 중복·동시성, 기존 함수와의 경합을 격리 DB에서 검증해야 한다. 이 방안도 유출된 서비스 키를 가진 호출자의 RPC 실행 자체를 막지는 못한다.
3. DB에서도 사용자별 권한을 강제하려면 검증된 사용자 JWT와 `auth.uid()`를 사용한 관리자 권한 저장소/RLS 설계가 필요하다. 사용자가 직접 수정할 수 있는 `user_metadata`에 권한을 두지 않는다. 이는 별도 설계와 승인이 필요한 범위다.

## Turbopack·Tailwind 최소 수정계획

현재 `npm run build`는 Turbopack CSS loader의 Node 자식 프로세스 연결 실패로 다시 실패했다. 기존 Webpack 대체 빌드는 종료 코드 0이지만 CSS에 사용 중인 `.w-full`, `.p-5`, `.bg-brand-navy`가 없고 원시 `@theme`이 남았다. 이번 가짜 키 Webpack 빌드도 보안 스캔 용도이며 스타일 정상성을 뜻하지 않는다.

별도 격리 브랜치에서 Next.js 로컬 문서의 `@tailwindcss/postcss` 설정과 기존 `@tailwindcss/turbopack` 규칙을 비교하고, 필요한 의존성·PostCSS 설정만 추가/교체하는 최소 후보를 만든다. 기본 빌드와 Webpack 빌드에서 실제 유틸리티 CSS가 생성되는지 확인하고 홈·강좌·일정·관리자 폼의 데스크톱/모바일 화면 및 키 비노출을 재검수한다. 근본 원인은 확정되지 않았으며 현재 설정·의존성은 변경하지 않았다.

## 적용 보류 및 다음 조건

실제 개발 DB, 운영 DB, 다른 프로젝트, main과 Vercel Production은 변경하지 않았다. 실제 공개 API는 강좌 5개·주차 60개·일정 0개를 HTTP 200으로 반환했다.

실제 Auth 계정이 해당 프로젝트에서 확인되고 로그인·허용/거부 절차가 통과해야 한다. 직접 쓰기 우회에 대한 권한 설계를 결정·격리 검증하고, 최종 SQL과 정확한 권한 변경을 다시 검토해야 한다. 그 후 기존 이력·객체·권한·데이터와 단일 후보 dry-run 및 트랜잭션을 재확인하고 명시적 DB 적용 승인을 받는다. 실패·타임아웃 시 재실행하지 않고 이력·객체·권한을 먼저 조회한다.
