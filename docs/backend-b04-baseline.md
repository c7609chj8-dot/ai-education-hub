신규 검수는 트랜잭션 적용·재적용 거부, 모든 신규 테이블 RLS·API 역할 및 기존 기수 실행 역할의 직접 접근 차단, 신청·기수·안내·개인정보 FK, 동일 기수 요청 키·개인정보 중복 제약, 잘못된 필드 거부, 개인정보 저장 실패의 거래 롤백, 취소와 자리 반환 필드 제약, 비어 있지 않은 롤백 거부를 시험한다. 롤백 전후 기존 함수 본문·소유자·ACL, 핵심 테이블 열·권한·RLS·정책과 공개 뷰 정의를 비교하고 관리자 저장이 다시 성공하는지도 확인한다.

PGlite 0.4.5의 새 메모리 인스턴스만 사용한다. 기존 테스트의 가상 auth.uid와 로컬 역할 모델은 실제 Supabase JWT·Auth 전체 시스템이 아니다. 기존 자동 RLS 함수는 저장소 fixture로 재현하므로 호스팅 이벤트 트리거 전체 동작 검증으로 해석하지 않는다. 요청 처리 함수가 아직 없으므로 실제 병렬 마지막 1자리·취소 경합·서버 접수 성공은 후속 거래 구현과 별도 두 세션 PostgreSQL 시험 대상이다.

## 화면 기준선과 모바일

브라우저는 로컬 127.0.0.1 서버에 연결하지 못했고, #35 Preview는 Vercel 인증 화면으로 이동했다. 접근 보호 설정은 변경하지 않았다. 기존 운영 도메인의 동일한 샘플 신청 화면을 모바일 기준선으로 사용했다. 이 관찰은 새 브랜치·인증된 개발환경의 모바일 통합 검수가 아니다.

GitHub blob SHA 대조에서 운영 main과 PR #35의 신청 페이지, 시연 신청 폼, 공통 CSS가 각각 동일함을 확인했다.

- 360 × 800에서 샘플 신청 빈 제출 시 이름·연락처·동의 오류가 표시되고 이름 입력란으로 초점이 이동했다. DOM 너비 검사에서 가로 넘침은 없었다.
- 390 × 844에서 가상 이름과 `010-0000-0000`을 입력하고 시연 확인 후, 실제 접수가 아님을 알리는 완료 화면과 제목 초점 이동을 확인했다. 가로 넘침은 없었다. 완료 화면 스크린샷을 도구 결과에 기록했다.
- 임시 브라우저 폭은 검수 후 복구했다. 이 화면은 브라우저 메모리의 시연이며 실제 신청 제출 시험과 구분한다.

현재 산출물은 다음 격리 구현을 위한 초안이다. 실제 접수 어댑터, 관리자 신청 원문 열람, 자동 취소·자리 반환·파기는 후속 정책과 권한 검토에 연결한다. 실제 개발 DB 마이그레이션과 데이터 변경, main 병합, 운영 배포는 이번 작업 범위에 포함하지 않는다.

종료 시 개발 DB를 같은 읽기 전용 쿼리로 재확인했다. 시작과 동일하게 마이그레이션 5건, 강좌 5·주차 60·기수 1·공개 기수 0이며 신청·개인정보 테이블은 없다.
