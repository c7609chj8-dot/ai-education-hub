# 백엔드 11일차: 신청 데이터와 서버 검증

작성일: 2026년 11월 7일

상태: **서버 전용 사전 검증과 비공개 데이터 구조 초안 준비, 격리 테스트 완료. 실제 신청 접수·저장 기능은 제공하지 않습니다.**

## 범위와 현재 환경

- 비회원 신청, 접수 즉시 정원 확보, 같은 기수의 같은 이름·연락처 중복 방지는 기존에 결정된 요구사항입니다. 이름과 연락처 표기 차이, 취소·반려 후 자리 복귀 및 재신청은 미확정입니다.
- 개발 DB `uenvjqgylrevujdjpfed`를 읽기 전용으로 확인한 결과 `academy`에는 기존 강좌·주차·기수 테이블 세 개가 있고 신청 테이블은 없습니다. 이번 작업에서 실제 DB, 마이그레이션 이력, 환경변수 또는 데이터를 변경하지 않았습니다.
- 기존 `/apply/[offeringId]`는 여전히 가상 입력만 확인하는 시연 화면입니다. 서버 검증 코드는 화면이나 공개 API에 연결하지 않았으며 실제 개인정보를 받거나 저장하는 경로를 추가하지 않았습니다.

## 준비한 내용

`src/lib/applications/validation.ts`는 서버 전용 사전 검사입니다. 대상 기수 UUID, 후보 필수 항목인 이름·연락처, 기관에서 승인한 안내 버전과 확인 여부, 기수의 공개·모집 중 상태와 강좌의 공개 상태를 확인합니다. 중복 필드나 위조된 버전도 거부합니다. 기수와 활성 안내 버전은 향후 **신뢰할 수 있는 서버 데이터**에서 가져와야 하며, 클라이언트가 제출한 상태를 신뢰해서는 안 됩니다.

모집 기간의 시작과 종료 시각은 둘 다 있어야 하며 시작은 포함, 종료는 제외하는 **임시 보수 규칙**입니다. 시간대가 포함된 시각만 허용합니다. 이 규칙과 한국 시간 표시, 기간이 없는 기수의 취급은 실제 운영 정책 확정 시 검토해야 합니다. 여기서의 검증 성공은 접수나 자리 확보를 의미하지 않습니다. 정원·중복·동시 변경은 후속 DB 트랜잭션에서 다시 검사해야 합니다.

`supabase/drafts/day11_application_data.sql`은 `academy.applications`와 `academy.application_private`의 검토용 초안입니다. 둘 다 RLS를 켜고 공개 역할과 서비스 역할의 직접 테이블 접근을 명시적으로 회수합니다. 사용 가능한 정책이나 쓰기 함수는 만들지 않습니다. 개인정보 분리는 접근 관리 설계일 뿐 암호화나 익명화가 아닙니다. 정책이 결정되기 전에는 초안을 정식 마이그레이션으로 취급하거나 적용하지 않습니다.

이름·연락처는 필요한 최소 정보에 대한 **후보**이며 실제 수집 목적, 필수 여부, 법적 근거, 안내·동의 방식, 보존 기간과 삭제 절차는 기관이 확정해야 합니다. 초안의 안내 버전과 확인 시각도 해당 결정에 따라 바뀔 수 있습니다. 임시 테스트 안내 버전은 실제 수집에 사용할 수 없습니다.

## 검사 결과

- `npm run test:application-validation`: 유효한 가상 입력, 누락·잘못된 값, 중복 필드, 오래된 안내 버전, 비공개·마감 기수와 시작·종료 경계를 검사했습니다.
- `npm run test:application-schema`: 메모리 PostgreSQL에서 RLS, 테이블 접근 차단, 외래키·안내 버전 제약을 확인했습니다. 기본 권한이 넓게 설정된 상황도 가정했습니다. 이는 실제 Supabase 역할 상속이나 API 접근 검사가 아닙니다.
- TypeScript, ESLint, Next.js 빌드와 기존 관리자·강좌·일정 격리 테스트를 확인했습니다. 10일차 테스트 파일의 ESLint 변수명 충돌은 이름만 수정했습니다.
- 실제 DB 쓰기, 실제 Supabase Data API, 관리자 계정과 실제 신청은 검증하지 않았습니다.

## 다음 작업과 미해결 사항

12일차에는 모집 상태와 정원을 DB에서 잠금 등의 방식으로 다시 확인하고, 신청 저장과 자리 확보를 하나의 트랜잭션으로 결합하는 방안을 설계·구현해야 합니다. 마지막 자리 경합, 중복 전송, DB 실패와 응답 유실 재시도도 검증해야 합니다. 이름·연락처 비교 규칙과 멱등성 기준은 기관 확인이 필요합니다. 13일차 화면 연결 전에는 안내·동의, 개인정보 보존과 악용 방지 정책, 실제 개발 DB 적용 및 API 권한 검증이 필요합니다.

8·9·10일차 SQL 초안은 미적용이며 기존 `public.rls_auto_enable()` 보안 경고 2건은 미해결입니다. 기존 보안 마이그레이션 초안은 이번 작업에 포함하지 않습니다. 실제 적용 시 현재 프로젝트의 역할 상속, 기본 권한과 API 노출 설정을 다시 점검해야 합니다. Supabase는 [테이블 접근 권한과 RLS를 별도 계층으로 설명](https://supabase.com/docs/guides/database/postgres/row-level-security)하며, [신규 public 테이블의 자동 API 노출에 관한 변경](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)을 공지했습니다.
