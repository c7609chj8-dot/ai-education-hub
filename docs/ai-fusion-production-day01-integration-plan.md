## 목적과 안전 경계

이 문서는 별도 공개 시연 프로젝트를 만들기 위한 계획이 아니다. 기존 GitHub 저장소와 기존 Vercel `ai-education-hub` 프로젝트를 정식 운영 가능한 홈페이지로 전환하기 위한 통합 기준선과 단계별 게이트를 정의한다.

1일차에는 코드·DB·Vercel 설정을 변경하지 않고, 현재 소스·PR·개발 DB·Vercel·백업 증거를 읽기 전용으로 확인했다. 다음은 이 문서의 고정 제약이다.

- `main` 병합, 기존 Vercel Production 배포, Supabase 운영 DB 변경은 최종 승인 전까지 하지 않는다.
- 개발 DB의 DDL·데이터·RLS·GRANT·RPC 변경은 백업 검증과 단계별 별도 승인 후에만 한다.
- A1/A2 후보 SQL은 이번 단계에서 실행하지 않는다.
- 기존 5개 강좌·60주차·비공개 시험 기수와 기존 관리자 RPC v2를 삭제·우회·덮어쓰지 않는다.
- 비밀번호, JWT, API 키, 덤프, 신청자 개인정보 및 로컬 환경 파일은 GitHub·PR·Preview·문서에 넣지 않는다.

### 현재 개발 DB의 구조적 사실

읽기 전용 메타데이터와 집계만 확인했다. 신청자 정보나 Auth 사용자 정보는 조회하지 않았다.

- `academy.courses`, `academy.course_weeks`, `academy.offerings`, `private_education.offering_admins`만 존재한다.
- 강좌 5건은 모두 `published`이고, 기수 1건은 `draft`, `is_public=false`다.
- `academy.applications`, `academy.application_private`는 아직 없다.
- v2의 내부 `SECURITY DEFINER` 함수는 `private_education`에, 공개 `SECURITY INVOKER` 래퍼는 `public`에 있다.
- 현재 `save_offering_v2`는 신청 테이블이 생기면 SQLSTATE `55000`으로 기수 저장을 차단한다. 이 보호 장치를 우회해서는 안 된다.
- Security Advisor에는 `private_education.offering_admins`의 RLS 무정책 INFO 1건과 leaked-password protection 비활성 WARN 1건이 있다. 전자는 직접 API 접근을 전부 회수한 비공개 관리자 목록 설계와 함께 검토하고, 후자는 운영 전 Auth 정책 결정 항목으로 관리한다.

### 현재 프런트엔드의 사실

- `src/lib/courses.ts`와 `src/lib/schedule-data.ts`는 `ACADEMY_COURSE_SOURCE`가 `supabase`일 때 공개 카탈로그/공개 기수 조회를 지원한다. 기본값은 mock이다.
- `src/app/apply/[offeringId]`는 mock 기수에만 동작하는 신청 **시연**이다. 브라우저에서 검증 후 입력값을 전송·저장하지 않는다.
- `src/lib/applications/*`에는 서버 입력 검증·idempotency 결과 해석의 초안이 있으나, 실제 DB 저장 어댑터·공개 Server Action/API는 없다.
- `src/lib/admin/applications.ts`와 관리자 신청 화면은 향후 RPC 이름을 참조하지만, 실제 DB에는 그 테이블·RPC가 없고 기능 플래그가 없으면 차단된다.
- `src/lib/supabase/config.ts`는 현재 개발 프로젝트 origin을 명시적으로 고정한다. 정식 운영 DB에는 개발 값 재사용이 아니라, 별도 승인된 Production 구성과 검증 가능한 환경 분리가 필요하다.
- Webpack 기준 현재 `/admin/demo` 및 그 하위 시연 경로는 정적 라우트로 남아 있다. 정식 운영 전에는 이 경로와 개발 진단 경로를 제거하거나 운영 환경에서 확실히 404 처리하고, 인증된 실제 관리자 경로만 남기는 라우트 감사를 수행한다.

1. 새 통합 브랜치 `codex/ai-fusion-production-integration`는 #37 HEAD에서 시작한다. #35 및 #30~#34를 다시 병합하면 중복·충돌 위험만 생긴다.
2. PR #36의 네 테이블 SQL 후보와 격리 검수 기록은 설계 입력으로 보존한다. 현재 상태에서 #36을 기계적으로 병합하지 않는다. 후보 DDL만 실제 DB에 적용하면 기존 `save_offering_v2`가 의도적으로 차단되기 때문이다.
3. 실제 신청 구현은 #36을 대체하는 하나의 검토된 변경 집합으로 만든다. 이 변경 집합은 신청 테이블, 원자적 접수 RPC, 관리자 기수 v3 거래 규칙, 회귀 테스트를 함께 포함해야 한다.
4. 이후 기능 브랜치는 모두 이 통합 브랜치에서 분기하고, 각각 Draft PR로 다시 통합 브랜치에 검토·Preview·회귀 검수 후 합친다. 기존 PR #30~#37과 `codex/b04-day01`은 기록과 비교 기준으로 보존한다.
5. 통합 브랜치에서 `main`으로 가는 PR은 계속 Draft로 유지한다. 최종 운영 승인과 전체 검증이 끝난 뒤에만 Ready/merge를 검토한다.

## 목표 아키텍처

### 공개 조회

- 승인된 공개 강좌·주차·기수만 읽는다. 신규 6개 학과가 실제 DB에 등록·검증되기 전에는 mock/시연 데이터와 실제 데이터가 섞여 보이지 않게 출처와 안내를 분리한다.
- 일정에는 모집 상태·정원·잔여석을 표시하되, 잔여석은 승인된 신청의 좌석 점유 수에서만 계산한다. 신청자 수·이름·연락처를 공개하지 않는다.
- 모집 상태, 공개 상태, 모집 시작/종료 시각이 하나라도 미확정이면 신청 버튼은 비활성화하고 정확한 사유를 안내한다.

### 비회원 신청

공개 폼은 이름·연락처·승인된 개인정보 수집·이용 동의 버전만 수집한다. 이메일, 주소, 생년월일, 자유 서술을 MVP 저장 항목에 추가하지 않는다.

1. 서버가 입력, 동의 버전, 공개 상태, 모집 기간과 rate limit을 먼저 검사한다. 브라우저가 전달한 기수 상태·정원·관리자 ID는 신뢰하지 않는다.
2. 동일 재전송을 복구할 수 있는 요청 UUID를 서버 검증 대상으로 두되, 다른 본문의 요청을 같은 키로 덮어쓰지 않는다.
3. DB 함수 한 트랜잭션에서 기수 행을 잠그고, 모집 상태/기간/공개 상태/중복/점유 좌석을 다시 확인한 뒤 신청·최소 개인정보·최초 상태 이력을 함께 저장한다.
4. 마지막 한 자리 경쟁에서는 같은 기수 잠금 아래 `seat_released_at IS NULL`인 신청만 점유로 집계한다. 실패 시 개인정보를 포함한 전체 거래를 롤백한다.
5. 응답은 접수·마감·중복·불확실 상태만 최소한으로 알려 준다. 타인의 신청 존재 여부, 원문, 연락처 또는 관리자 판정 근거를 노출하지 않는다.

직접 테이블 접근은 `anon`, `authenticated`, `service_role`, 기존 `academy_offering_executor`에 부여하지 않는다. 공개 접수는 서버 전용 저장 경로에서만 호출하며, API 키는 브라우저로 보내지 않는다. IP 기반 방어는 신청자 DB에 IP를 저장하지 않는 Vercel Firewall/승인된 rate-limit 계층을 우선 검토한다.

### 관리자와 기수 v3

기존 `academy_is_admin_v2`의 실제 Auth 사용자 + DB 관리자 목록 이중 검증은 유지한다. 신청 도입 시 별도 버전의 관리자 거래를 설계한다.

- 기수 정원 축소, 강좌 이동, 모집 상태 변경, 취소 및 자리 반환은 신청 접수와 동일한 기수 잠금/점유 규칙을 사용한다.
- 정원보다 이미 점유가 많아지는 저장은 거절한다. 신청 테이블 존재를 감지한 뒤 전체 기능을 멈추는 현재 v2 보호는 통합 v3가 검증되기 전까지 그대로 둔다.
- 관리자 목록은 기본적으로 이름 마스킹·연락처 끝 네 자리만 표시한다. 원문 열람은 별도 권한·목적·감사 기록이 승인된 경우에만 최소 범위로 설계한다.
- 모든 privileged 함수는 고정 `search_path`, 명시적 스키마, 최소 EXECUTE, 독립적인 현재 사용자/관리자 검증을 사용한다. `user_metadata`나 브라우저 actor ID를 권한 근거로 쓰지 않는다.
